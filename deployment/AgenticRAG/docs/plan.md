### 1.1 问答与研究报告

已确认两类使用场景，共同要求跨文档查证、比较、推断及带引用输出；报告深度与形式已确认 D08，具体模板、保存接口与验收规则仍待设计。

- 问答围绕具体问题组织结论和证据；研究报告围绕主题或比较维度组织章节、结论、分歧与资料不足。
- 两类输出复用同一套数据、检索、原文读取和引用能力，不建设两套 RAG 核心。
- 已选择结构化报告：现有 Agent 按任务需要多次检索和读取，再组织为 Markdown，可保存为文件。内容包含结论、必要的对比、证据、局限及引用；具体章节按任务组织。
- 首版不实现分阶段研究计划、逐章节撰写与复核的专门工作流。Agent 仍可按问题需要拆解查询、自主补查；具体次数和预算后续确认。
- 当前 MultiHop-RAG 继续用于检索与问答质量对照；报告的问题覆盖、综合结论和逐结论引用，需要另定验收方式，不能直接用短答案题的分数替代。

### 1.2 数据生命周期

已确认 D09：首版具备基本增删改及历史引用读取能力。冻结评测数据与日常知识库可更新分别设计。

- 导入：新文档完成处理并发布后，后续新任务可检索；已开始的任务继续使用原版本范围。
- 普通批量导入：按 D30 发布成功处理的部分，失败新增文档不参与检索，失败更新文档保留旧版本；失败情况明确列出，详见 1.18。
- 更新：成功发布后新任务使用新内容；正在运行的任务及历史报告引用仍指向各自绑定的版本。
- 删除：成功发布后该文档不再参与新任务检索；已开始的任务仍可检索和读取其绑定版本中的文档。保留历史引用所需原文，删除不等同于彻底清除所有历史材料。
- 历史引用：读取保存的相应版本，不以已经变化的源文件替代当时的原文；按 D31 保留全部历史原文及必要定位信息，不自动清理。
- 评测：每次运行固定语料及其版本，避免把资料更新造成的变化误认为算法变化。

一次 Agent 多轮检索期间的版本一致性已确认 D12，具体行为见 1.5；文档身份规则已确认 D18，见 1.9；历史原文全部保留已确认 D31，见 1.19；闲置历史索引自动回收已确认 D32，见 1.20。后续需明确路径规范化等匹配细则及发布、失败恢复和回收机制。D09 的历史引用要求适用于新模块今后产生的报告；按 D10，不接续旧 CodePlus RAG 的数据格式与既有引用。

### 1.3 旧实现退役与新方案边界

- 新模块按新存储契约建库，所需原文重新导入。旧 `generation_id`、旧索引 schema 和旧引用 ID 不构成新设计的兼容约束。
- 用户另行授权独立清理任务，实际删除旧 RAG 实现、专属接入及不再需要的依赖，并同步调用方、测试和文档；该授权不等同于启动本任务的新 RAG 实现。
- 清理任务保留通用 CodePlus Agent 与工具执行能力，保护本目录及当前 MultiHop-RAG 数据、数据校验与离线评分能力。
- 不兼容旧格式不等于需要删除用户原始文件、运行数据、已有报告、模型缓存或 Milvus/Docker 数据。清理任务不操作这些数据。
- 清理任务在隔离工作区交付可审查改动；创建或启动任务不代表清理已经完成，实际接入新模块时以已集成的宿主状态为准。

### 1.4 知识库范围

已确认 D11：可以创建多个库，一次任务只使用用户明确选择的一个库。一个库内可包含多篇文档，跨文档推断不需要跨库检索。

已确认 D52：这里的单库范围与检索要求适用于使用知识库功能的任务。知识库问答或报告通过搜索取得材料；普通聊天或其他未使用知识库功能的任务不附加强制检索。已配置知识库、工具可用或默认采用自动检索模式，本身不等于所有消息都需要搜索。

设计约束：

- 一次问答或报告开始时绑定库 ID；本次检索、原文读取和引用校验始终使用该范围。选择其他库后发起新的任务。
- 由宿主/适配层约束库范围，Agent 不凭自行生成的库 ID 扩大搜索或读取范围。
- 核心服务可以管理多个库，不因此引入跨库路由、自动选库或合并排名。
- 评测使用单独选择的评测库，防止日常资料混入冻结语料。
- 验收包含库隔离：两个库中即使出现相同词语或相同原件，也只返回当前选定库的证据；跨库读取引用不能绕过范围检查。

同一库在任务期间发生更新时，按 D12 使用本次绑定的知识库版本，不能悄然切换到最新版。

### 1.5 一次运行内的版本一致性

已确认 D12：一次问答或报告开始时选择该库已发布且可查询的版本，本次所有搜索、补查、原文读取及引用都绑定该版本。更新成功发布后，新任务使用新版本，当前任务继续完成。

由此得到的设计约束：

- 知识库版本需要确定本次可见的文档版本集合和对应索引配置；仅记录一个版本号不足以保证实际读取一致。
- 旧版本在运行期间必须仍能搜索尚未命中过的文档，不能仅缓存第一次检索结果来代替固定版本检索。
- 新文档、修改后的内容及删除状态不渗入已开始的运行；同一次运行的 Dense、BM25、融合、Rerank 和原文读取使用一致的语料范围。
- 新版本准备完成后才对新任务可见；发布失败不能让新任务绑定不完整版本。具体索引布局、发布机制及失败恢复实现待技术设计验证。
- D30 允许普通批次中的文档处理部分失败；发布的版本仍须完整表达最终可见集合，即成功变更、未变文档及更新失败文档的旧版本。文档处理部分成功与知识库版本只发布一半是不同情况。
- 报告与运行记录保存库 ID、知识库版本及实际使用的文档版本，使引用可定位。
- 活跃运行所需索引和原文不得提前清理。运行结束后，按 D31 仍保留全部历史原文及引用定位信息；历史检索索引按 D32 在确认不再使用后自动回收，不能只根据创建时间或版本先后决定删除。

验收场景：运行 R1 绑定版本 V1 后，更新/新增/删除文档并发布 V2；R1 的后续搜索及读取保持 V1，新运行 R2 使用 V2，两个运行各自的引用均能定位对应原文。普通文档更新发布失败时，仍应能从最后一个完整版本开始新运行；更换 Embedding 的重建失败另按 D16 提示并等待用户选择，不把保有可用旧版本等同于用户已经决定继续使用它。

### 1.6 回答依据与资料不足

已确认 D13：问答与报告的事实结论只依据当前任务、当前绑定知识库版本实际取得的材料。模型可帮助理解问题、组织表达和改写查询，但其自身知识不构成事实证据。

- 允许跨文档比较、计算和推断，需能指出支持结论的证据；涉及推断时明确表达推断及其依据，不将推测写成原文事实。
- 部分问题有依据时给出该部分结论与引用，同时明确未覆盖的问题及缺少的材料。
- 完全缺少依据时允许直接说明无法从现有资料作答，不为满足格式而编造结论或引用。
- 文档相互冲突时说明分歧并引用双方材料；是否能够判断适用时间、范围或优先级，应由材料本身支持。
- 搜索没有命中、命中但不足以回答、工具执行失败、运行预算耗尽分别记录；不能将工具失败称为资料不存在。
- 评测既检查无依据结论，也检查可回答问题被过度拒答的情况；引用 ID 可解析不等同于该引用支持结论。

Agent 在证据不足时仍可改写问题、再次搜索或读取原文。预算用尽后的交互方式已确认 D14；具体上限及其他提前停止条件仍待设计。

### 1.7 运行预算与结束行为

已确认 D14：预算达到上限时停止本次补查，利用已经取得的证据输出结果，注明未完成部分与预算停止原因。运行中不询问是否追加预算；用户可以另发请求继续研究。

已确认 D54：知识库问答和研究报告分别配置预算。问答倾向较快完成，报告允许更多搜索、阅读与整理时间；这是功能内的运行配置，不引入两套 Agent、检索实现或分阶段报告工作流，也不改变普通聊天和编程任务。

设计约束：

- 搜索次数、原文读取次数、模型调用与 Token、耗时的计量范围和具体上限后续统一定义，不在澄清阶段随意锁定数值。
- 问答/报告任务类型与固定/自动检索模式是两个独立维度：预算按本次知识库任务类型装配，检索权限按已选模式装配。运行开始时记录实际预算及来源，运行中不因修改配置或 Agent 自行改变输出形式而升级预算。
- 两类预算使用同一计量与停止机制。查询生成、改写、检索与阅读、重试、引用修正和最终整理的开销均须纳入相应统计；模型排队与切换耗时仍按 D40/D41 计入耗时，不能因阶段变化重置预算。具体计数、Token 口径和截止时间契约由技术设计确定。
- 在总预算内为最终整理答案预留 Token 和时间，接近探索预算上限时转入输出阶段；不得用“整理结果”为由无限追加调用。
- 如硬超时或模型故障导致无法完成整理，返回已取得的证据与明确的未完成状态，不能把中断称为完整答案或报告已保存。
- 运行记录区分证据充分完成、资料不足、预算停止和执行失败。仅有部分有依据的结果时，不将整道问题标记为完整解决。
- 预算耗尽不证明知识库没有答案。答案与评测记录要说明是检索未完成，不能将这一状态冒充已充分查证的无答案结论。
- 用户明确要求继续研究时按 D55 承接进度，建立新运行并记录本轮预算及绑定版本；上一轮的用量和停止原因保留，不覆盖或重置原运行记录。
- 报告有较大的可用预算不代表必须执行更多轮次；已有证据充分时仍可结束。两类任务的质量、成本与耗时分别报告，比较固定/自动模式时在相同任务类型下使用可比预算，避免将额外预算的收益误归因于检索策略。

已确认 D55：同一会话中用户明确要求“继续研究”时，承接原目标、已有发现和待查问题，优先补查缺口。新请求建立新运行，绑定开始时最新已发布且可查询的版本，并按 D54 分配本轮预算；关联上一轮运行，分别保留各轮状态及用量，也可汇总整段研究成本。

- 进度记录保存目标、已覆盖/待查问题、用户约束、先前发现的来源线索与停止原因，不保存或依赖模型内部推理。它是续研提示材料，不另建规划器或分阶段报告执行引擎。
- 历史答案及其引用不直接成为本轮证据。即使知识库版本未变，正式引用仍须通过本轮工具调用取得并登记；版本变化时从当前绑定清单定位来源，重新读取或检索。已删除或无法在本轮取得的材料不能冒充本轮知识库依据，发生变化的先前结论须注明修订或仍待验证。
- 继续研究仍限于 D11 所选同一个库；换库视为新任务，不将旧库证据带入当前事实依据。无法确定上一轮研究目标或记录缺失时说明缺口并澄清，不能凭空恢复进度。
- 仅由用户的新请求启动本轮，不自动延长旧运行、不在后台继续研究。上轮输出保留，后续报告建立新的产物及运行关联，不静默覆盖历史报告。

验收覆盖：预算停止后继续补查、已完成任务继续深入、同版本重新取证、期间发布新版本或删除来源、跨库阻断、进度记录缺失、各轮预算独立且累计成本可追溯，以及旧报告与引用仍可读取。

### 1.8 文档导入与更新触发

已确认 D17：用户选择文件或目录，手动发起导入或更新；系统检查所选范围并识别文档变化。首版不持续监听目录，也不因源文件发生变化就自动发布新知识库版本。

设计约束：

- 导入到明确指定的知识库，输入范围由用户选择；读取到的原件按 D09/D12 保存并形成可发布的文档版本。
- 系统区分新增、内容变化、未变化、处理失败等结果，记录本次处理范围与结果数量，不能把部分失败报告为全部成功。
- 原件与相关处理配置均未变化时避免重复解析和 Embedding。模型、分块或影响索引的配置变化时另做兼容检查，不能仅因文件哈希相同就跳过必要重建。
- 再次导入目录时，目录中未出现的已有文档不自动删除；删除由用户明确发起，沿用 D09 的历史引用保留规则。
- 文件身份按 D18 和 1.9 匹配；不能用文件名或内容哈希混作所有场景下的唯一身份。
- 批量部分失败按 D30 发布成功部分并保留失败更新的旧版本；目录遍历边界、发布实现与重试材料的保存细则在后续契约中确定。

### 1.9 文档身份、改名与移动

已确认 D18：在同一知识库中，同一路径内容变化视为已有文档的更新；改名或移动后的新路径默认导入为新文档。用户也可明确选择“更新已有文档”，延续所选文档的身份和历史。

由此得到的设计约束：

- `document_id` 是稳定身份，路径是导入匹配与来源信息，二者分开保存。同名但路径不同的文件不能仅凭文件名合并。
- 同路径内容变化时保留 `document_id`，登记新的内容版本；原件和相关处理配置均未变化时按 D17 避免重复处理。
- 不同路径即使内容相同，默认仍是不同来源的文档；内容哈希用于变化识别及可选的存储去重，不据此自动合并文档身份。不启用模糊内容匹配来推断改名或移动。
- 改名或移动后按默认方式新增，不自动删除旧文档；用户可显式删除旧文档，或在导入时选择更新已有文档。
- 显式更新必须选择当前知识库中的既有文档，保留其身份；历史版本中的来源路径和原文保持可追溯。遇到新路径已归属于另一文档等冲突时明确报告，不静默覆盖。
- 路径规范化、符号链接、已删除文档重新导入，以及仅路径变化但原件不变时的版本登记方式，留待对象与导入契约设计，不从本决策推导额外自动合并行为。

验收覆盖：同路径修改、同名不同路径、相同内容不同路径、改名/移动默认新增、指定已有文档更新、路径冲突、跨库更新被拒绝；每种情况下核对文档身份、当前来源与历史引用。

### 1.10 首版解析与 Chunk 切分

已确认 D19：采用“文档结构＋句子边界＋Token 上限”。先按标题、段落组织，过长时继续拆分，尽量保留完整句子。块大小与重叠量可配置；首版不依赖模型计算语义分界，保留后续替换策略的接口，是否引入语义切分由评测决定。

设计约束：

- Markdown 解析保留标题层级、段落及列表、表格、代码块等结构信息；纯文本按实际段落和句子处理，不虚构章节或页码。具体解析库、句子识别规则仍待选型验证。
- 在结构范围内组织 Chunk，尽量保持语句完整；单句或结构块超过上限时仍需可追溯地继续拆分，不能为保留结构而越过模型输入上限，也不能静默丢弃剩余内容。长表格、列表、代码块的具体拆分规则在解析契约中明确。
- Token 计数按所选 Embedding 的实际输入规则验证，计入最终拼接的标题、前缀及特殊 Token 等开销；字符数和正文 Token 数不能冒充实际输入长度。查询模型的 Context 预算另行计算。
- 块大小和重叠量暂不固定数值，模型选定后通过冻结语料上的对照评测确定；重叠的计量、范围与边界规则同配置版本一起记录。
- Chunk 保存文档版本、结构位置和对应原文范围；检索文本中的标题前缀与真正的证据正文区分，拼接结果不冒充一段连续原文。重复句子、换行格式和 Unicode 不应导致来源定位到错误位置。
- 切分策略通过明确接口替换，不把具体库对象直接作为核心对外契约。记录解析器、切分器、配置及影响结果的 tokenizer 身份，必要时重新构建候选索引；不直接改写已发布版本中的 Chunk。
- 切分库选型或升级需验证原文映射、输入长度边界和检索效果；本决策不等于沿用旧 SentenceSplitter 实现、旧参数或旧验收结论。

验收覆盖：普通段落、嵌套标题、重复文本、超长句、表格/列表/代码块、CRLF 与 Unicode、重叠片段，以及标题和特殊 Token 加入后的长度上限；检查内容覆盖、来源可定位、相同输入与配置的结果可复现。原文读取范围已确认 D20，见 1.11。

### 1.11 原文读取与分页

已确认 D20：`knowledge_open` 默认打开命中片段所在章节，长章节分页返回。Agent 可以继续读取文档其他章节，或在预算允许时逐步读取全文；不要求每次搜索后都自动打开全文。

设计约束：

- 从搜索结果提供的来源标识定位文档与章节，始终使用 D11/D12 绑定的知识库及已发布版本，不用当前源文件或最新版替代保存的对应原文。
- 默认阅读范围是所在章节，单次返回仍有长度上限。长章节的首次返回应能定位到命中位置；提供章节导航与继续读取的位置，使 Agent 可以补读前后内容及其他章节。嵌套标题的章节边界、首次窗口规则在工具契约中明确。
- 对没有标题的 Markdown 或纯文本，以命中位置及有界正文范围开始读取，并支持分页遍历文档；不能因没有章节而一次塞入整篇长文或拒绝读取。
- 返回文档、版本、章节及准确原文范围，明确本次已返回范围、是否还有内容和续读标识。分页是工具响应分段，不伪造文档页码；局部返回不能标成“全文已读取”。
- 续读标识绑定文档版本和阅读范围，校验后才能使用；不能通过跨库、过期或错配标识越过运行范围。新版本发布期间，连续读取仍保持原版本，预算允许的完整遍历不遗漏正文。
- 按已保存的原文及来源映射读取，不把含重叠的检索 Chunk 直接拼接冒充连续原文。结构展示和标题导航与引用证据区分。
- 原文读取结果同搜索片段一起登记为本次可引用证据；仅返回目录、存在未读章节或提供续读标识，不代表其正文已经进入 Agent Context。
- 单次返回量、累计阅读量、Token 与耗时计入 D14 的运行预算，并为最终输出预留空间；具体上限后续确定。预算停止、文档结束、无效定位与读取失败使用不同状态。

验收覆盖：短章节、长章节首读与续读、命中在章节中部、跨章节阅读、无标题文档、嵌套标题、完整遍历的内容覆盖、精确来源映射、错配续读标识、读取期间发布新版本，以及预算停止时的部分结果与未读状态。

### 1.12 固定检索与自动检索两种模式

已确认 D21/D22：两种模式同时纳入方案，都保留 Agent 改写问题、多轮搜索和原文阅读能力。固定模式按配置执行每次检索；自动模式还允许 Agent 选择本次检索方式。这里的“固定”只限定单次检索流程。

已确认 D24/D53：知识库问答与报告功能内部默认采用自动检索。用户可修改该功能的默认模式，也可在每次知识库问答或报告开始前显式选择本次模式；该默认值不全局生效，也不预先证明自动模式的质量或成本更优。

| 维度 | 固定检索模式 | 自动检索模式 |
| --- | --- | --- |
| 单次检索流程 | 按配置执行，例如 Dense＋BM25 → RRF → Rerank；示例不等于已锁定默认配置 | 按 D23 选择 Dense、BM25 或 Hybrid，并选择是否启用 Rerank；实际可用选项受运行能力约束 |
| 数量与融合参数 | 由配置确定 | 同左；Agent 不调整候选数量、融合参数和返回片段数量 |
| 多轮补查与改写 | Agent 可改写 query、多次搜索、读取原文，遵循运行预算和停止规则 | 同左；额外具备在允许范围内选择检索方式的能力 |
| 数据与证据 | 使用共同的知识库、索引、来源、版本与引用契约 | 同左；模式不会扩大知识库范围或更换绑定版本 |
| 执行能力 | 复用同一检索核心，执行配置指定的路线 | 复用同一检索核心，执行本次合法选择的路线 |

设计约束：

- 区分“运行采用的固定/自动模式”和“某次搜索实际采用的 Dense、BM25 或 Hybrid 路线”，不把自动模式直接当成 Hybrid 的别名。
- 按 D53，固定/自动模式归属知识库问答与报告的配置域，只在该功能运行时解析并约束检索行为。即使由 CodePlus 统一配置文件保存和加载，也不成为通用 Agent、普通聊天、编程任务或其他工具的全局模式；不复用宿主权限模式的字段语义。
- 处于固定模式时，每次搜索使用绑定的检索流程与参数；Agent 可调整问题表述和决定是否补查，但不能通过工具入参暗中改换检索路线。固定流程也不意味着必须搜索预设次数，达到证据或预算停止条件时按共同规则结束。
- 模式选择不直接修改文档、Chunk 或索引身份；可用检索路线由绑定版本的索引能力与运行配置共同约束。检索方式选择不能触发未经确认的模型更换或索引重建。
- 按 D23，自动模式对检索流程的选择限定为检索方式和 Rerank 开关。选择由程序校验，不能随意调用未接入的检索器、扩大库范围、调整模型配置或提高预算。
- Dense、BM25 两条召回路线各自执行；Hybrid 执行两路召回及 RRF 融合。Rerank 可对任一所选路线的候选重排；关闭时沿用该路线的排序。首版支持这些组合，实际可用性还需检查绑定版本的索引及模型能力。
- 候选池数量、RRF 参数、Rerank 候选上限和返回片段数量由配置控制，并记录实际执行参数。返回片段数量是上限，结果不足或 Context Token 预算更小时允许少返回，不能靠补入无关内容凑数。
- Agent 工具层不开放上述数值覆盖权限；内部检索服务可供配置装配和评测使用，不能因内部接口可传数值就允许 Agent 绕过约束。核心仍对解析后的参数做合法性检查。
- 选择不可用的路线或 Rerank 时返回明确状态；能力不可用、候选为空、主动关闭重排和执行失败分别记录。按 D25 将错误交给 Agent 处理，不由程序自动改换路线或跳过失败阶段，具体行为见 1.13。
- 两种模式共用 D13 的证据要求及 D14 的运行预算；自动选择所需的模型调用、Token 和时间同样计入成本。
- 记录运行模式、请求的检索路线、实际执行路线与参数、各阶段结果、失败及 Agent 随后选择的处理方式；不把未执行的 Rerank 或失败的一路召回报告为成功。
- 仅在知识库问答或报告功能内，模式解析优先级为本次知识库任务显式选择 → 该功能配置默认值 → 该功能默认自动检索；任务级覆盖不隐式改写功能默认值，不向功能外任务传播。配置字段名与具体交互入口后续随宿主接入设计确定。
- 在运行开始时绑定并记录最终模式及其来源，后续修改默认配置不改变已开始的运行。Agent 只能在当前模式允许的范围内行动，不能自行把固定模式改为自动模式。
- 模式值或配置不合法时明确报告，不将拼写错误、能力不可用等问题当作“未指定”而悄然采用默认值；检索能力故障按 D25 处理。

验收增加两种模式的真实调用路径、允许选项校验、范围与预算约束、实际路线可追溯，以及相同冻结题集和可比预算下的质量、Token 与时延对照。不预设自动模式优于固定模式。固定模式须覆盖改写 query 后再次搜索、读取原文并形成引用的完整场景，检查多轮搜索仍执行绑定流程。自动模式按 D23 覆盖三种检索方式与 Rerank 开/关的组合、不可用能力处理、禁止数值越权、候选不足与预算约束下的返回结果。

模式选择验收包括：知识库功能未配置模式时使用自动检索、功能默认固定模式、单次知识库任务覆盖配置、覆盖不修改功能默认值、运行中修改默认值不影响当前任务、非法模式被拒绝，以及运行记录能还原最终模式的选择来源。按 D53 验证修改或覆盖该模式不改变普通聊天、编程任务、其他工具和宿主权限模式的行为；不因设置了功能默认值而自动启用知识库检索。

单次“检索 → 回答”可作为后续评测基线，不能用它替代 D22 已确认的固定模式产品行为。自动模式权限由 D23 确定，默认值与任务开始前选择由 D24 确定，功能内作用域由 D53 确定；具体入口及其余配置参数取值仍待设计。

### 1.13 在线检索与重排失败

已确认 D25：检索或 Rerank 失败时，工具返回明确错误，由 Agent 决定预算内的后续动作。自动模式可按 D23 重新选择检索方式或关闭 Rerank 后再次调用，也可按原配置重试；固定模式只能按原检索配置重试，仍保留 D22 的 query 改写和原文阅读能力。两种模式都可以停止补查并返回已有的有效证据及未完成说明。

设计约束：

- Hybrid 中任一路召回执行失败，本次请求报告失败，不把另一条成功路线的结果自动当作成功的 Hybrid 结果；Rerank 执行失败时也不自动将未重排候选作为该请求的成功结果返回。
- 成功执行但没有命中，与工具失败不同。Hybrid 中某一路成功返回空结果时，可由另一条成功路线贡献候选；两路都成功且为空时返回正常的无命中状态。无候选时无需调用 Rerank，记录为无候选未执行，不伪造模型故障。
- 错误信息包含失败阶段、错误类别、可用的后续动作或能力信息，并与本次调用关联。超时、暂时不可用、参数错误、能力缺失等需可区分；具体错误码与可重试判断在工具契约中定义。
- 失败调用的阶段中间结果可用于诊断，但不自动冒充本次成功取得的证据进入 Context。此前成功取得的证据仍可使用，不能因后续某次失败而丢弃，也不能据此声称失败调用成功。
- 自动模式的下一次改选是新的显式工具调用，记录失败与后续调用的关联及实际路线。它不修改运行模式、模型配置、库范围或绑定版本。固定模式不得以故障处理为由跳过配置要求的召回路线或 Rerank。
- 失败尝试、重试和改选后的调用均计入 D14 的搜索/调用、Token 与耗时预算；具体计数及连续失败停止阈值后续统一确定，不在任何层无限重试。结束时区分工具故障、预算停止与资料不足。
- 本规则针对在线搜索与重排，不替代 D16 的 Embedding 更换和索引重建流程；后者仍按已确认的“提示重建 → 用户确认 → 自动构建 → 失败时重试/保留原版”处理。

验收覆盖：Dense/BM25 故障、Hybrid 单路故障与单路正常空结果、Rerank 失败与候选为空、自动模式显式改选后成功、固定模式不绕过配置、重试后仍失败、预算耗尽以及失败后的有效证据保留；验证错误不会被报告成无资料或完整成功。

### 1.14 Context 证据选择

已确认 D26：对成功检索的结果，以相关性为先，去重后兼顾不同来源。相关性接近时优先保留不同文档中的互补证据；不为增加文档数量而加入明显不相关的内容，也不强制每篇文档只能选一个片段。片段数量与 Token 上限同时生效。

设计约束：

- 选择发生在当前检索路线完成排序之后：启用 Rerank 时采用其有效排序，关闭时以该路线的排序为基础。Context 选择不能暗中启用已关闭的 Rerank，也不能把 D25 的失败中间结果作为成功候选使用。
- 区分候选池、实际选入的片段和最终呈现给 Agent 的证据；记录选择、去重、裁剪及未选入的原因，使召回损失与 Context 选择损失可以分别检查。
- 同一文档版本内重复或重叠片段减少重复占用；保留独有信息、准确原文范围与有效引用。不同路径的相同内容可在展示层减少重复，但必须保留各自来源，不改变 D18 的文档身份，也不把重复来源误算为多份互补证据。
- 来源覆盖是相关性相近时的选择偏好，不设置未经确认的文档数配额或每文档硬限制；同一文档有多条必要证据时可以同时保留。不能把不同文档中的冲突证据当作重复信息删除。
- “相关性接近”、互补性和去重规则的具体算法及参数待设计、评测后确定；不同检索路线或不同 query 的原始分数不可直接当作统一尺度比较。不在本决策中额外引入 LLM 选择器或语义模型调用。
- 片段数量与来源文档数量分别统计。数量与 Token 限制按配置及当前剩余预算执行，Token 计算针对实际发送给回答模型的正文、引用标记与必要元数据；连同宿主已有上下文和最终输出预留共同约束，不能只统计 Embedding 输入或每次工具响应后就视为总 Context 合规。
- 需要裁剪时保留准确范围与截断状态，不将分散片段拼成连续原文，不把未返回的内容标为已阅读。原文继续读取仍按 D20 的版本、分页与预算规则执行。
- 多轮搜索与原文阅读累积后的证据保留、跨轮去重、宿主 Context 压缩及引用持续有效的具体契约，后续结合 CodePlus 通用上下文管理设计，不默认把全部候选永久留在模型输入中。

验收覆盖：同文档重叠片段、相同内容不同来源、相近相关性下的互补文档、单文档独有关键证据、多文档相互冲突、候选不足，以及片段数/Token 上限同时触发时的裁剪与引用定位；在冻结问题上同时检查证据覆盖、Context Relevance 和答案表现，不把文档数量增加当作效果提升。

### 1.15 输出前的引用校验

已确认 D27：首版在答案或报告正式输出前进行程序化引用校验，不为每次输出额外调用模型逐条复核语义支持。结论是否真正得到证据支持、引用是否覆盖关键事实，纳入评测与人工抽检；D13 的证据约束仍适用于生成过程。

程序校验范围：

- 引用标识能够解析，且指向本次运行成功取得并呈现给 Agent 的证据；仅存在于索引、候选池、未读章节或失败调用中间结果的材料不自动获得可引用资格。
- 引用所属知识库、知识库版本、文档版本及来源位置与运行记录一致；按保存的对应版本核对，不替换为当前源文件或最新版。
- 原文范围真实存在，来源元数据与权威记录相符。文件名、章节、行号等从来源记录取得；Markdown/纯文本不伪造页码，跨片段内容不冒充连续原文。
- 输出包含直接原文摘录时，核对摘录与其引用范围内的原文是否匹配；若允许换行等格式归一化，须定义可复现规则并保留原文映射，不能用语义相似代替引文匹配。转述与推断不能标为逐字原文。
- 对每项声明的引用记录检查结果与具体错误，区分未知标识、运行范围不符、版本错误、位置无效、摘录不匹配及核对所需材料读取失败；后者不能冒充已通过或资料不存在。

校验边界与验收：

- 程序通过仅表示引用可追溯且声明的摘录符合规则，不表示该引用支持对应结论，也不保证所有事实都已附引用。语义支持与引用覆盖不自动标为通过，应由对应评测或人工检查另行给出结果。
- 首版不增加每次回答必经的模型语义复核链。未来如引入，需独立定义质量收益、成本、失败处理与运行预算；当前不把该扩展列为首版已实现能力。
- 问答与 Markdown 报告共用校验规则。流式草稿、最终输出、报告保存之间的接口需保证校验状态清楚；校验未完成或失败的内容不能宣称为已校验完成的正式结果。失败时按 D28 进行至多一次修正，见 1.16；具体交互和保存接口另行设计。
- 验收包含有效引用、伪造标识、跨库/跨版本引用、未返回的候选、越界位置、重复原文误定位、摘录篡改、来源读取失败，以及“引用合法但不支持结论”的样例；最后一类用于证明程序校验与语义评测分别记录，不要求程序凭位置校验识别语义错误。

### 1.16 引用校验失败后的有限修正

已确认 D28：初次程序校验失败时，将具体错误反馈给原 Agent；剩余预算允许时，给出一次修正机会并重新校验。修正后仍失败、修正执行失败或剩余预算不足时，返回未完成状态、失败原因与仍可核对的有效证据。

- 修正只在程序校验失败时触发，初次通过的答案不增加此轮调用；这不是 D27 已排除的每次必经模型语义复核。
- 修正输入包含待修正输出、结构化校验错误与本次有效证据标识。沿用原运行的知识库、版本、模式与证据范围；不得换库、换版本或伪造引用来消除错误。
- 每次问答或报告运行最多一次引用修正机会，针对全部已发现错误统一处理。修正版重新执行完整引用校验，不能只检查旧错误，也不能因出现新错误再启动第二轮修正。
- 修正调用及耗时计入 D14 的总预算，不重置探索额度、不追加预算；输出阶段的预算设计应考虑修正与最终状态返回。预算不足则直接结束为未完成，不等待用户追加额度。
- 修正仍遵循 D13：可以纠正引用、调整摘录或删除无法支持的结论并说明缺口，不能通过删除引用标记而保留无依据断言来冒充成功。D27 的程序校验能力边界保持不变，不因此宣称完成了语义支持核验。
- 校验通过后才交付正式答案或报告；未通过时返回可用证据与明确的未完成说明，不把失败草稿当作正式报告。报告实际保存成功与引用校验通过分别记录。
- 记录初次与再次校验结果、修正是否触发、修正次数、用量及最终状态，保留排查所需的输出关联；有限修正不能掩盖初次错误率。

验收覆盖：初次通过且零修正、多个错误经一次修正后通过、修正版新增错误、修正模型调用失败、再次校验失败、预算不足跳过修正，以及未完成结果中有效证据与失败状态的准确交付。确认修正计数不会按引用条目或工具调用重置。

### 1.17 使用入口与内部评测

已确认 D29：日常使用沿用 CodePlus 现有基础命令形式，不另建一套独立产品命令体系或本地 Web 界面。“评测入口”仅指开发时批量运行固定问题、记录结果和评分的内部脚本，不是用户必须使用的另一套界面或操作流程，也不取消初始请求中的评测工作。

本轮只读核对的命令事实与接入方向：

- `pyproject.toml` 将 `codeplus` 指向 `codeplus.__main__:main`。现有终端支持普通对话及斜杠命令，现有 `codeplus -p` 提供非交互运行形式。
- `codeplus/commands/handlers/knowledge.py` 当前提供 `/knowledge create`、`use`、`import`、`status`、`sources`、`remove`、`open`、`off` 等命令。新方案沿用这类操作形式管理知识库、选择范围、导入资料和查看来源；选库后通过正常提问或报告请求调用真实 CodePlus Agent。
- 当前 `-p` 路径可通过 `--knowledge` 指定库。新实现的命令契约需同步验证选库、运行模式、状态与错误输出；沿用命令形式不代表直接保留旧 handler、旧 KnowledgeContext、旧引用 ID 或数据结构，D10 的退役边界不变。
- 当前 `--mode` 表示权限模式，不是固定/自动检索模式；新检索模式的配置或命令参数不能覆盖其既有语义。具体参数、帮助信息和任务开始前的选择方式在接入契约中确定。
- 新 RAG 核心、适配层与后续功能仍在 `deployment/AgenticRAG/` 开发。接入现有命令所需的装配方式和最小宿主接点应单独列明并验证；不能以命令沿用为由提前复制多份业务实现，或依赖待删除的旧 RAG 模块。
- 评测复用 `eval/RAG-eval/` 的冻结语料、题集、数据检查及离线评分脚本；现有依赖旧 RAG 引擎的批量运行部分需要改接新核心与同一 Agent 路径，不直接视为新模块已可用。内部验证代码不另写检索、生成或引用业务逻辑。

验收要求：通过熟悉的基础命令完成建库、选库、导入、问答、报告及来源查看；交互与非交互接入按统一核心契约返回结果，模式选择不改变原有权限参数含义。开发评测与日常调用使用同一实现，不能仅凭内部脚本通过就宣称用户命令已接入成功。

### 1.18 普通批量导入的部分成功与重试

已确认 D30：普通文件/目录批量导入中，成功处理的文档可以发布，失败文档列出原因并支持重试；某文档更新失败时继续使用其旧版本。此规则不用于跨 Embedding 配置混合发布，更换 Embedding 仍遵循 D16 的候选重建与确认流程。

已确认 D47：一次手动导入的整批文件处理结束后，将成功变更统一发布一次。整批处理结束允许包含成功、失败及未变化的文件，不要求全部成功；处理期间不分批发布已完成的文档。

设计约束：

- 文档成功须包含该文档所需的归档、解析、分块、元数据和索引处理均完成，不能只完成部分 Chunk 就将该文档标为可发布。
- 失败新增文档不进入新版本；失败更新保留该文档最后已发布的版本。失败候选内容不覆盖原件、来源映射或旧索引数据。未涉及及未变化的文档保持原状态。
- 按 D47 在整批处理结束后，根据成功变更与需保留的文档版本形成完整候选版本，再按 D12 校验并发布一次。原文、元数据、Dense 与 BM25 可见范围须一致；若库级校验或发布本身失败，保留上一个可查询版本，不能把“处理完成”报告为“已经发布”。跨存储的原子可见与恢复机制仍需在技术设计中确定。
- 汇总分别报告已发布的新增/更新、未变化、处理失败和未发布的处理结果；逐文件记录原因及后续动作。部分成功不能显示为全部成功，更新失败时应明确该文档仍使用旧版本。
- 重试聚焦失败项或未完成发布的操作，已发布且输入/配置未变的成功项不重复处理。重试沿用 D18 身份规则，并核对输入与配置是否变化；防止重复建文档、重复生效或覆盖之后已经发布的新更新。输入快照、恢复记录及并发控制细节随后设计。
- 没有任何成功变更时不为了凑批次进度发布一个虚假的新内容版本；正常无变化、全部文档处理失败及库级发布失败分别报告。不存在可查询版本时明确说明，不能假称保留了旧版。
- 发布后新任务使用该版本，已开始的问答或报告继续使用原绑定版本；部分失败不改变 D12 的运行一致性与 D09 的历史引用要求。
- 冻结语料的正式评测须另行检查全部预期文档及版本齐备。日常允许发布部分成功的库，不代表该库已经满足完整评测语料要求；缺失材料不能被静默剔除后报告为完整验收成绩。

发布与中断边界：

- 发布前，新问答继续绑定之前已发布的版本；首次建库尚无已发布版本时明确说明，不暴露候选数据。发布后新问答使用新版本，已开始的问答仍按 D12 使用原版本。
- 例如本批 100 个文件中有 90 个成功、10 个失败，将 90 个成功变更与应保留的旧文档版本一起校验并发布一次；失败更新保留旧文档，失败新增不加入。没有成功变更时不创建新版本。
- 取消、进程崩溃或连接中断不能视为正常整批处理结束，也不触发“先发布已完成部分”。若中断发生在发布附近，恢复时先核对权威发布记录和资源状态；不能仅凭客户端未收到成功响应，就断言未发布、再次发布或回退已经发布的版本。具体状态字段与幂等协议随后设计。
- D39 的同库修改互斥覆盖整次正常导入及发布；异常后核实拥有者与任务状态再恢复占用。D41 的 GPU 推理小批次只决定调度，不是知识库发布批次，也不提前释放修改占用。

已确认 D48：普通批量导入中断后保留进度，用户再次执行相关命令时提示未完成任务，由用户手动选择继续。复用已完成且校验有效的结果，处理剩余工作后按 D47 统一发布；重新启动程序本身不触发自动续跑。

续跑设计约束：

- 进度与恢复依据须持久化，至少能够关联知识库、批次、原基准版本、输入范围、逐文件内容身份、处理配置、已完成阶段及产物、错误和实际发布记录。不能只保存百分比或内存队列；具体字段、检查点粒度和写入协议随后设计。
- 首版要求同一安装环境中退出并重新启动后的恢复。复用范围以可验证的持久化结果为准，不承诺从某次 GPU 计算的内部位置继续；计算完成但尚未可靠保存的部分可重新计算，已验证完整的文档不应整篇重做。
- 恢复先核对拥有者、任务执行状态及实际发布记录。原任务仍在运行时按 D39 提示忙，不能并行接管；若已发布但成功响应丢失，返回既有发布结果，不重复创建版本。无法确认状态时明确提示待核对，不把不确定状态当作成功或直接覆盖。
- 用户选择继续后，按 D39 取得修改执行权，再核对基准版本、输入及配置身份和产物完整性。按 D50 校验本批次保存的输入快照，按 D51 恢复本批次原处理配置；源文件或当前默认配置后来的变化不使匹配原快照与原配置的结果失效。实际执行环境无法满足原配置、结果缺失或损坏时，不得复用失效结果，需明确指出原因及受影响部分，不把不兼容模型结果混入一个文档版本。
- 未完成阶段继续处理；明确失败的项目仍按 D30 列出原因并支持重试，不进行无限自动重试。候选在整批完成并校验发布前不可检索，恢复失败不破坏原已发布版本。
- 按 D32 保护恢复依赖的候选索引与相关进度材料；清理前须确认已无恢复依赖，不仅凭进程退出或文件年龄判断。D31 的历史原文和引用信息仍受保护。等待恢复期间的同库修改限制按 D49；主动放弃后的资源释放遵循下述边界，具体清理协议仍待设计。
- 交互和非交互继续沿用 D29 的现有命令形式。非交互续跑须能显式指向未完成任务；缺少选择时返回可操作状态，不无限等待输入。具体命令和参数留待接入契约定义。本决策针对普通导入，不替代 D16 的 Embedding 更换确认与失败选择流程。

已确认 D49：同库存在待恢复的普通导入时，先继续完成或主动放弃，再启动新的导入、删除或重建。已发布内容仍可查询，其他知识库不受这条修改限制；共享模型和存储资源仍按各自容量与调度规则使用。

等待恢复与主动放弃的设计约束：

- 待恢复状态持久化，所有同库修改入口均检查它，并返回任务标识、状态以及继续/放弃的操作提示。不能仅因原进程退出、运行锁过期或程序重启，就把业务上的未完成任务当作不存在；具体跨进程协议随后设计。
- 等待用户选择期间不持有长时间 SQLite 写事务，也不持续占用 GPU。查询的版本绑定、占用记录和结果保存仍可进行；索引回收继续遵循 D32 的依赖保护，不能把禁止新修改等同于禁止一切元数据写入。
- 继续与放弃须互斥，并核对任务拥有者和实际发布状态。只有一个进程能推进该任务；主动放弃须使原执行者及迟到结果失去写入或发布该候选的资格，再解除同库新修改限制。实现需避免旧进程恢复运行后覆盖新任务，不能只删除一条锁记录。
- 主动放弃不发布已处理的部分，也不撤销已成功发布的版本。若核对发现此前发布已完成，应报告既有结果，不将其误作未发布候选删除。正常整批完成并按 D30 汇总的部分成功任务已经结束，失败文件的清单不无限占用知识库；后续重试按新的修改操作取得执行权。
- 放弃后保留必要的任务状态和结果记录。仅确认无依赖的未发布候选索引及临时产物可进入清理；用户源文件、已发布版本、活跃运行所需索引、D31 的历史原文及引用定位信息继续保留。先确保候选不可再发布，再按清理协议回收资源；清理失败应记录并可重试，不伪报已完成。

已确认 D50：续跑使用本批次导入时保存的文件快照，完成原批次；源文件后来的修改通过下一次导入更新。

输入快照设计约束：

- 在解析和 Embedding 前固化本批输入清单及逐文件快照结果，记录原始来源、文档匹配身份、内容哈希、字节长度、采集时间及归档引用。每个可处理文件须有完整且可验证的保存内容；不能只保存原路径后在续跑时重新读取。具体采集与落盘协议随后设计。
- 正常处理和续跑均读取同一份不可变快照，解析、Chunk、来源定位与索引内容保持对应。源文件后续修改、删除或移动不改变已保存的快照；输入清单固化后新增的文件不自动进入原批次。来源仍保留导入时的路径和身份，不把内部快照路径当成用户来源。
- 快照按文件采集，不宣称整个目录在同一瞬间完成系统级快照。采集时发现文件正在变化，应明确失败或在原采集阶段有界重试，不能将不完整副本当作稳定原件；批次记录各文件的实际采集结果。
- 若中断发生在快照准备阶段，已保存且校验通过的文件可以继续；未保存完整、缺失或无法验证的文件明确列为快照失败，不静默补入恢复时的最新内容。只有能校验为原记录相同内容的完整原件才可用于修复；不能证明一致时留待新批次重新导入。若连输入清单也未可靠保存，明确报告该批次无法续跑，不假造原输入范围。
- 快照失败按 D30 报告：更新失败保留已发布旧版，失败新增不进入候选；其他成功内容在整批结束并校验后按 D47 统一发布。所有输入失败或无成功变更时不发布新版本；正式评测仍要求冻结语料齐备，不能跳过缺失材料后报告完整验收。
- 快照与正式原文归档可复用相同存储内容，保留各自身份与引用，避免不必要的物理副本；不以内容相同合并文档身份。恢复依赖按 D32 保护，正式历史归档继续按 D31 保留；临时碎片不能登记为完整档案。容量不足时明确失败并保留旧版，空间、哈希及持久化校验机制随后设计。

已确认 D51：导入及续跑固定使用该批次记录的原处理配置，新配置用于后续操作；需要 Embedding 重建时仍按 D16 提示确认，原模型不可用则明确报错。

处理配置设计约束：

- 在开始处理前保存已解析的配置及身份，覆盖解析器与版本、分块参数与 tokenizer、Embedding 模型及 revision、输入模板、维度和编码约定，以及本次索引构建所需的 BM25/索引配置。不能只保存一个会被重新指向其他模型的 profile 名称；具体字段和兼容指纹在模型与索引契约中确定。
- 续跑读取批次记录，不重新套用当前默认值；共享模型工作进程按该记录解析实际模型身份。已有结果的复用以原输入、原配置与产物完整性共同判断。恢复前显示本次实际使用的配置及其与当前配置的差异，不回写或覆盖用户后来保存的新配置。
- 原模型 revision、tokenizer、解析组件或其他必要依赖无法取得，或当前环境不能满足原执行约定时，明确报告无法按原配置继续，保留进度和原已发布版本。用户可恢复所需环境后再次继续，或按 D49 主动放弃；不自动选择新模型、混用新旧 Chunk 规则或切换 CPU/API。
- 固定的是影响处理结果的配置与兼容身份，不要求原进程永久存活或模型在等待期间持续占用显存。进程重启后的实际依赖与模型身份必须重新核验；不把相同名称或相同向量维度当作兼容证明。凭据只保存引用，不把密钥写入配置快照、指纹或日志。
- 新默认配置与当前批次实际配置分开记录。后续操作仍先检查与现有库的兼容性，需要 Embedding 重建时按 D16 确认并构建候选；不得因结束旧批次就自动绕过确认切换新索引。普通导入沿用已有版本与任务状态机制，不另建配置切换工作流。

验收覆盖：新增成功/失败混合、更新失败保留旧版、成功文档可检索、失败文档无半成品暴露、全部失败、全部未变化、文档处理成功但库级发布失败、失败项重试、重复重试、重试前已有新更新，以及发布期间活跃运行与历史引用的版本一致性。按 D47 增加整批结束前候选不可见、成功批次只发布一次、新库首次发布前的明确状态，以及发布前后中断和成功响应丢失时的状态核对。按 D48 增加真实进程退出并重启、未选择时不自动续跑、已完成有效结果复用、未持久化结果重算、损坏或不兼容产物拒绝复用、重复继续及两个进程竞争恢复、恢复失败仍可查询旧版，以及恢复材料不被提前回收。按 D49 增加待恢复时各修改入口一致拦截、旧版查询与其他库修改可用、继续和放弃竞争、放弃后迟到结果不能发布、完成或放弃后可发起新修改，以及放弃不删除历史数据。

### 1.19 历史原文与引用定位信息保留

已确认 D31：首版保留新模块产生的各版本原文及必要引用定位信息，不按时间、版本数量或是否已被报告引用而自动清理。适用范围是新模块的文档历史，不改变 D10 对旧 RAG 实现退役及旧格式不迁移的约定。

设计约束：

- 纳入文档版本记录的已归档原件按对应版本保留，源文件修改、改名、移动或删除不改写已归档内容。文档从新任务检索范围移除后，其历史版本仍可用于引用回看。
- 保留原件之外，还要保留核对引用所需的内容哈希、文档及版本身份、当时的来源信息、原文位置和解析映射；不能只保留原始字节而丢掉定位旧引用所需的数据。
- 必要的解析文本、Chunk 来源映射及引用记录属于历史追溯数据，不能仅因检索索引被替换就清除。未来解析器或切分策略变化时，不用新解析结果覆盖旧引用的定位依据。
- 原文与定位信息的读取应独立于历史检索索引是否存在；保留原文不等于承诺任意历史版本始终可重新搜索。新任务仍受 D11/D12 的知识库与版本范围约束，历史引用回看不把已删除文档重新加入当前检索结果。
- 相同内容允许在存储层去重，但各文档身份、版本与来源关联完整保留，遵循 D18。临时下载碎片、临时调试材料等不因本决策成为永久历史档案；正式归档数据与临时数据须明确区分。
- 首版不自动删除历史原文来腾出空间；归档空间不足时明确报告并保留已发布版本，不在导入失败时破坏既有历史材料。需要主动永久清理时应另行设计用户操作及其影响，当前不增加默认清理流程。
- 历史检索索引按 D32 自动回收确认不再使用的部分，保护当前可查询版本、活跃运行及尚未完成的构建/恢复操作所需数据；回收不能删除本节约定的历史原文与定位信息。

验收覆盖：连续更新多个版本、改名/移动、删除后回看、未曾被报告引用的历史版本仍可读取、解析策略改变后旧引用可定位，以及存储去重不合并身份。索引回收能力实现后另验历史引用读取不依赖被回收的索引；不能把保留策略文档当作已经执行过恢复验证。

### 1.20 历史检索索引自动回收

已确认 D32：确认不再使用的历史检索索引自动回收。当前版本、运行中任务以及重建或恢复流程所需索引继续保留；无法确认使用状态时暂不清理。该规则适用于新模块管理的索引，不涉及用户原始文件、D31 的历史档案或其他服务数据。

设计约束：

- 回收资格与 D12 的版本绑定、发布及运行释放使用同一套权威状态。只有已退出当前可查询版本、没有运行引用、且无构建/重试/恢复依赖的索引才可进入回收流程；不能只按时间、版本数量或内存中的计数推断闲置。
- 运行绑定与回收之间需有并发保护，避免检查闲置之后又被任务绑定。进程异常退出、状态缺失或恢复尚未完成时保守保留，待核实占用状态后再判断；具体锁、租约或事务方案在存储设计中确定。
- D16 的模型切换等待确认、构建、失败待选择或重试期间，原版所需索引继续受保护。候选残留是否可清理由构建与恢复状态决定，不能因一次构建报错就破坏可重试材料或原版。
- 以实际索引存储单元核对归属和依赖。若多个保留版本共享集合、分区或向量数据，不能因其中一个版本过期而删除仍被其他版本使用的数据；Dense 与 BM25 的清理范围均须明确。
- 回收仅删除符合条件的检索数据，不级联删除原件、必要解析文本、Chunk 来源映射、引用记录、知识库版本清单或索引配置元数据。历史引用仍能定位原文；对应历史版本的可检索状态应准确更新。
- 记录待回收对象、资格依据、执行结果与错误。删除失败或中途退出不能记为已完成，也不能扩大清理范围；后续可幂等恢复，正常发布的当前版本仍应可查询。执行触发时机、重试和退避参数留待实现契约定义。

验收覆盖：当前版本不可回收、活跃运行结束前旧索引保留、占用释放后符合条件的索引被回收、绑定与回收竞态、进程异常后的状态核对、模型切换失败与重试保护、共享索引数据、清理中断恢复，以及清理后历史原文和引用定位仍有效。

## 3. 建议调整的推进顺序

下面是建议，具体范围和验收数值尚未锁定。

1. **范围、数据与评测协议**：冻结语料、题档、配置、基线和运行记录格式；确认开发调参题与最终验收题如何区分。
2. **数据准备**：原件归档与文档身份 → 解析与来源位置 → Chunk 与映射 → 版本登记 → Embedding 与 Milvus 索引。
3. **检索基线与混合检索**：分别验证 Dense、BM25，再比较两路召回经 RRF 融合的结果。
4. **Rerank 与 Context 构建**：候选重排、重复内容处理、跨文档证据保留；同时约束片段数和实际 token 数。
5. **Agent 集成**：由现有 CodePlus Agent 调用检索与原文读取，通过预算和停止条件约束补查、改写与回答。
6. **端到端验收与迁移**：在固定配置下完成检索、回答、引用、成本与性能对照，再验证 CodePlus 接入与兼容。

来源和版本从数据准备阶段贯穿所有步骤；评测从基线开始逐阶段运行，最终阶段再执行全量验收。

Hybrid Retrieval 表示 Dense 与 BM25 两条召回路径及其融合，不是位于 Vector Search 之前的另一条串行处理步骤。RRF 按排名融合；后续模型 Rerank 再判断 query 与候选内容的相关性。二者分别记录参数与分数，不将 RRF 分数当作概率。

### 4.4 核心执行 RRF

已确认 D43：首版由 RAG 核心分别获取 Milvus 的 Dense 与 BM25 结果，再执行 RRF；核心保留两路原始候选及排名，支持故障处理、观测和评测。Dense/BM25 索引继续由 Milvus 管理，首版不同时维护另一条服务端 RRF 执行路径。

Milvus 官方提供用于 Hybrid Search 的 RRF ranker。RRF 根据各路排名融合，属于检索融合步骤；后续 Embedding/Rerank 提供方中的模型 Rerank 另行执行。[Milvus RRF Ranker](https://milvus.io/docs/rrf-ranker.md)

融合契约草案：

- 本次 Hybrid 搜索的两路绑定同一 query、知识库、版本和过滤范围，并使用已固定的索引目标；不能在两次请求之间分别解析“最新版本”。只请求 Dense 或 BM25 时沿用该路排序，不额外执行两路融合。
- 以 Chunk 身份合并，同一路对同一候选只计一次贡献。建议首版采用等权 RRF：各路排名从 1 开始，候选的融合分数为其实际出现各路的 `1 / (rrf_k + rank)` 之和；`rrf_k` 由配置确定，具体数值后续评测选择。缺席某一路时该路不贡献分数，不补造排名。
- 记录每路原始候选、排名、分数及类型，保留融合分数、顺序和实际参数；RRF 分数不视为置信度。同分排序采用可复现规则，具体规则随接口定稿；不将不同 query 的历史结果直接视为本次两路召回。
- 每路召回数量、融合后送入 Rerank 的候选上限和最终进入 Context 的片段/Token 上限分别记录，具体数值仍由配置及验收确定。日志中的候选不因被记录就取得 D27 的“已交给 Agent 的证据”资格。
- 单路正常空结果允许另一成功路线的候选参与融合；任一路执行失败则本次 Hybrid 失败，遵循 D25，不把另一条成功结果包装成完整 Hybrid。成功融合后按本次配置决定是否调用模型 Rerank。

验收覆盖可手工核算的排名样例、两路重合及各自独有候选、重复 ID、单路/双路正常空结果、同分可复现、单路失败，以及发布切换期间两路仍绑定原版本。正式评测调用同一核心融合实现；融合正确性与最终答案质量分别验证。

### 4.5 逐 Chunk Rerank

已确认 D44：首版以召回的每个 Chunk 为独立排序单元，保留候选身份与原文位置，需要更完整上下文时由 Agent 按 D20 调用 `knowledge_open`。精排前不合并同一文档的相邻 Chunk。输入模板、候选上限及超长输入处理仍待设计与实测。

设计与验收约束：

- Dense/BM25 单路排序或 Hybrid 经 RRF 融合后的候选，按配置上限送入 Rerank；每个候选明确关联知识库、版本、文档和 Chunk。两路命中同一个 Chunk 时只保留一个候选，不因来源路线不同重复精排。
- 模型结果按候选 ID 对应原始内容，改变排序不改变身份及来源；分批推理后还原整个候选集的排序。相邻 Chunk 可以各自入选，同一文档多个互补片段继续按 D26 处理，不以本决策引入文档配额。
- 输入模板、query、标题/章节信息与 Chunk 内容的实际 Token 合计需符合选定 Reranker 限制，不能只依据 Embedding 的分块上限认定输入一定适配。超长处理需记录实际评分范围，不静默丢弃候选、改写归档原文或伪造完整输入已评分。
- Rerank 评分、原始检索分数及 RRF 分数分别记录。批次失败按 D25 报错，不用已完成的部分评分或融合顺序冒充完整重排结果。
- 精排后的 Context 选择仍受 D26 的相关性、去重、来源互补和双重预算约束。内部参与 Rerank 的候选不自动取得 D27 的证据资格，只有实际交给 Agent 的内容才可用于其引用；需要扩展原文时继续按 D20 返回并登记证据。

验收覆盖同一文档相邻候选、两路重合候选、批次结果重组、候选 ID 与引用映射、真实模型输入长度、候选为空、部分批次失败，以及精排候选与最终可引用证据的区别。Rerank 排序有效性仍需与关闭 Rerank 的同条件结果比较，不能由接口成功推断效果提升。

### 4.6 问答语言与跨语言验收

当前 `eval/RAG-eval/README.md` 明确：官方基线为英文新闻语料与原题，未加入中文改写，也不覆盖中文效果。D45 已在产品范围中补充跨语言问答，官方题集保持不变。

已确认 D45：支持中文提问英文知识库、用中文组织答案，直接引用的原文保持英文。英文评测基线继续采用原题及其语言约定；跨语言功能另行验收，不把所有输出全局改为中文。

设计与验收要求：

- 跨语言验收仍以现有英文语料为基础，派生中文问题单独标识并记录原题关联及版本，不修改官方问题、答案和 gold。具体样例数量与类型随后确定，派生问题需核对语义等价及约束是否保留。
- 记录原始中文问题、每次实际检索 query 及其语言、所选路线、取得的证据与中文答案。改写应保留实体、时间范围、比较条件和否定条件；原题 gold、答案及证据标注只进入评分环节，不进入 query 生成或被测 Agent。
- 中文解释、推断和结论仍遵循 D13，直接摘录保留可定位的英文原文并按 D27 校验。若附译文，作为说明标识，不替换原文摘录或伪装为原文逐字引用。
- 检索以原证据位置检查命中与覆盖，中文答案另按语义正确性、Faithfulness、问题覆盖和引用支持评估；不以英文字符串匹配单独判断中文答案。跨语言结果与官方英文基线分别报告，程序引用校验不替代语义质量验证。
- 评测沿用相同新核心及真实 CodePlus Agent，固定语料、模型、配置和可比预算，记录查询改写及补查的 Token、轮数与延迟。端到端通过不自动证明 Embedding 或 Reranker 可以直接处理任意跨语言输入，模型能力按实际调用语言另行验证。
- 本次确认覆盖中文问题检索英文资料；中文文档语料及更多语种的完整检索质量仍需另行定义验收，不由本决策推定已覆盖。

已确认 D46：英文检索 query 由现有 CodePlus Agent 生成和改写，再调用 `knowledge_search`。Agent 使用已有的对话模型配置；检索核心及共享 Embedding/Rerank 工作进程不增加独立翻译或改写模型步骤。

- Agent 根据原始问题及本次运行实际收到的结果生成 query；结果不足时可以改写或拆分问题后继续搜索、打开原文。生成与补查沿用现有 Agent 循环及 D14 的运行预算，不额外开启一套不限额流程。
- 固定模式和自动模式均允许改写 query、多轮搜索与 `knowledge_open`，遵循 D22。固定模式保持检索路线不变；自动模式的路线及 Rerank 选择仍受 D23 约束。
- 核心执行工具实际提交的 query；必要的输入校验和模型/分词器预处理不承担语义改写。一次 Hybrid 搜索的 Dense、BM25 和后续 Rerank 使用同一提交 query；Agent 改写后再次调用属于新的搜索事件，仍绑定原运行的知识库版本。
- 记录原始问题、每次工具提交的 query、调用结果、轮数、Token 与延迟，包含 Agent 生成和改写的成本；以工具参数与可观测事件作为审计依据，不要求记录模型内部推理。通过实际样例检查实体、时间、比较与否定约束是否保留，接口调用成功不能替代语义验收。
- 纯检索英文基线直接使用原题 query；Agentic 与中文派生题测试使用真实 Agent 生成的实际 query，分组报告质量与成本。任何测试的答案和 gold 均不得进入 query 生成。保留用户中文问题用于回答和评分，英文改写不覆盖原问题、原文或索引内容。

## 6. Agent 行为草案

```text
使用知识库功能的任务 → CodePlus Agent
                  ├─ 搜索知识库 → 获得证据片段与可读取的来源标识
                  ├─ 证据不足 → 拆解／改写问题 → 再搜索
                  ├─ 需要上下文 → 打开相应版本的原文或章节
                  └─ 证据充分／预算耗尽 → 有引用的回答／明确说明不足
```

- `knowledge_search`、`knowledge_open` 暂作概念名称；最终命名与输入输出契约后续确定，不以继承旧 RAG 工具名为前提。
- 按 D52，使用知识库问答或报告功能时调用搜索取得材料，再根据结果决定补查、打开原文和回答。未使用该功能的任务不因 RAG 模块存在而增加检索步骤；知识库的创建、导入、状态查看等管理操作也不应为了满足搜索次数而调用检索。
- 按 D21/D22 支持固定与自动两种检索模式，均使用前述 Agent 循环。搜索次数、问题改写和原文补查由 Agent 在预算内决定；固定模式的每次搜索按配置执行，自动模式按 D23 额外允许选择 Dense/BM25/Hybrid 和 Rerank 开关，数量与融合参数仍由配置控制。
- 按 D24/D53，仅在知识库问答或报告功能运行开始前解析本次选择及功能默认值，未指定时使用该功能默认的自动检索，并将最终模式作为检索约束传入。Agent 不自行改变用户选定的模式，功能外任务不继承该约束。
- 按 D25 处理检索与重排错误：自动模式可在允许范围内明确改选后再调用，固定模式保留原检索配置；不由服务自动降级，失败和重试都计入预算。
- 一次任务的所有搜索和原文读取均限定在 D11 选定的单个知识库及 D12 绑定的同一版本中。
- 按 D13 仅以取得的知识库证据支持事实结论；部分有依据时部分回答，完全不足时明确说明，不能用模型记忆补齐。
- 按 D14 在预算达到上限时停止补查并返回当前结果与缺口，不等待追加预算；需要为最终输出预留预算。
- 后续明确问题拆解规则、最大搜索/读取次数、总 token 与总耗时预算，以及工具调用和正式结果交付的检查点。
- 重复查询无新证据、工具故障、绑定版本不可用、相互冲突的证据与不可回答问题应有明确结果；不能在绑定版本不可用时静默换用最新版。正常发布新版本不构成当前任务的停止条件。
- “证据足够”不能等同于 RRF 分数达到阈值或命中数量够多；应考察各子问题是否有支持材料。
- `knowledge_open` 按 D20 默认读取所在章节，可在预算内分页读取其他章节或全文；只将实际返回的正文登记为本次证据，不把导航或未读内容当作已经取得的依据。
- 原文和工具输出不成为执行指令；工具作用域由程序绑定。
- 按 D27 在正式输出前校验声明的引用。Agent 生成时仍需遵守证据要求，程序校验通过不代表语义支持或事实正确；首版不自动增加每次必经的模型复核步骤。
- 初次引用校验失败时按 D28 向原 Agent 反馈具体错误，预算内最多修正一次并完整重校；仍失败或预算不足时交付未完成状态和可用证据，不无限修正或输出失败草稿作为正式结果。
- 运行记录保存可观察的调用、结果和状态，不依赖模型私有推理过程。

第 49 轮已撤回“强制首轮搜索／不强制”的独立选项，按 D52 明确功能边界。该决策不锁定工具首次调用顺序，也不要求每条消息重复搜索；实现须保证声称基于知识库的资料结论有真实取得的证据，遵循 D13/D27。任务澄清、取消、检索失败和正常无结果应准确表达，不能用一次空调用满足计数后就把无证据内容作为正式资料结论。具体接入和检查机制由后续技术设计确定，不再要求用户为此选择 A/B。

## 7. 验收框架草案

按 D56，首版优先保证证据与答案质量，同时遵守预算上限。具体质量、延迟、资源和费用阈值按基线与冻结程序填写，不先随意指定百分比；不能仅为降低时延就静默降低证据支持要求。

| 层面 | 预期检查 | 如何避免误读 |
