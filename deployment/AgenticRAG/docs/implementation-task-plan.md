**完整交付目标：R00–R26 全部 27 项任务实现或完成其规定交付、逐项通过 checklist 并本地提交，且 checklist 总体验收全部通过。** R12/M1 是中间验证节点，验收提交后必须继续 R13–R26；任何阶段通过均不构成提前结束整个项目的条件。不以最小问答链路或演示可用缩减已确认首版范围。

## 1. 依据、优先级与实施边界

Leader 开始前读取以下文件；执行者至少读取分派任务关联章节：

1. [主规划](plan.md)：D01–D56 是已确认的需求。不要根据旧实现、历史报告或语料正文增加需求。
2. [架构与接口契约](architecture-and-contracts.md)：T01–T09 规定当前工程方案、对象、状态及工具契约；其中试验参数须实测冻结。
3. [验收与阶段计划](acceptance-and-implementation.md)：G0、P0–P8、A01–A15、数据/评分口径和质量目标冻结程序。
4. [模型配置](model-providers.md)、[部署与迁移](deployment-and-packaging.md)：模型切换、部署和分发边界。

适用优先级：用户最新明确指令 → D 决策 → 已审阅的接口/状态契约 → 本任务拆分与 checklist。发现矛盾时记录具体条目和影响；常规实现细节由 Leader 决定并同步文档，改变已确认范围或质量/成本取舍才交给用户。不得通过修改 checklist、降低阈值或标记“不适用”绕过需求。

本任务表细化 P0–P8 的执行顺序：把首次发布、Dense、原文和 Agent 的必要部分前移到 R10–R12，先得到真实链路，再补齐完整生命周期与检索能力。其余已确认需求仍是首版发布门槛，没有被移出范围。

特别保持：独立核心复用现有 CodePlus Agent；Markdown/TXT 首版；多库管理、单运行单库及固定版本；功能内 fixed/auto，默认 auto；两种模式均可多轮搜索/阅读；程序不静默降级；实际交付正文才能作为本轮证据；QA/报告分别预算；继续研究重新取证；质量优先但预算有界。旧数据兼容、PDF/OCR、CPU 与多用户服务不纳入首版。

## 2. Leader 的执行与提交流程

### 2.1 一项任务一个闭环

默认按 R00 → R26 串行推进，一次只安排一个写代码的执行会话。表中列出的前置是最低技术依赖；前一项未验收提交，不提前启动下一项写入任务。只读调查或独立评审可以由其他会话承担，不能同时改同一工作区或争抢真实 GPU/测试库。

R00 由 Leader 负责接管，可委派只读核查；从 R01 起逐项创建执行会话。R00 的台账会话栏记录 Leader，本身只交付规划输入与基线，不包含业务实现。

每项任务按以下顺序执行：

1. **准备**：Leader 检查前置提交、spec 版本、工作区基线和可用环境，填写任务分派单。
2. **分派**：创建一个执行会话，给出任务 ID、目标、允许文件、禁止范围、基线、关联 spec、任务 checklist 和交付格式。不能只发“实现 RAG”。
3. **执行**：执行者完成实现、必要的正式测试与文档，提交结果给 Leader；不自行提交、推送或宣布验收通过。
4. **验收**：Leader 独立检查改动及证据，执行适用的通用检查和该任务全部条目。存储发布、恢复/回收、宿主和迁移等高风险改动，可另开只读评审会话；最终结论由 Leader 负责。
5. **修复**：存在问题则退回原执行会话，说明失败条目和复现依据。修复后重验受影响项及回归；不能先提交再补必需检查。
6. **提交**：所有必需项通过、审阅范围与最终补丁一致后，Leader 精确暂存并创建本地 commit，验证提交内容与 SHA。
7. **交接**：记录结论、提交、未完成范围和下一任务，然后继续下一项，无需逐阶段询问是否继续。只有 R00–R26 全部 COMMITTED 且 checklist 总体验收全部通过，才能宣布整体完成。用户明确暂停/调整范围或确有无法继续的阻塞时中断，列出未完成项和恢复条件；会话切换时保存进度并续接，不能把中断当作完成。

验收通过后本地提交已由用户授权，后续不为每个正常任务重复请求提交许可。此授权不包含 push、发布、合并远端 PR 或清理无关用户数据，也不代替产品内 D16 的模型重建确认流程。

### 2.2 工作区、会话与 Git

- R00 先选定唯一集成工作区/分支。当前计划文件位于 `D:/CodePlus/deployment/AgenticRAG/`；接手时重新检查实际路径和 Git 状态，不假设历史分支名仍有效。
- 本轮检查时该目录尚未被 Git 跟踪，仓库还有继承改动。新 worktree 从已提交状态创建时可能不含规划、评测更新或必要依赖；不能只根据 HEAD 就认为输入齐备。
- 默认可在明确选定的集成目录串行创建执行会话，只有一个写入者。若采用独立 worktree，必须从 Leader 当前验收基线创建，并核对 spec、数据和依赖清单；由 Leader 以 patch/精确文件转移结果，不让执行者提前 commit 充当验收。
- R00 对继承修改、新文件及已暂存内容保存路径/哈希清单。Leader 只提交本任务经过审阅的文件或 hunks；同文件已有改动必须区分归属。禁止 `git add .`、批量 reset、随意 stash 或把继承删除一起带入。
- 评审冻结 `base SHA + tracked diff + 新文件内容哈希 + 配置/数据指纹`。只有 `git diff` 看不到未跟踪文件，必须检查完整新文件。
- 提交前重新核对暂存差异，确认它就是通过验收的改动。评审后代码变化使相关结论失效；须重验后再提交。
- 一项任务默认一个本地提交，建议标题 `feat(rag): Rxx ...`、`test(rag): Rxx ...` 或 `docs(rag): Rxx ...`。修复在验收前完成；不靠反复 amend 制造通过记录。
- 在 commit 后记录真实 SHA：该 SHA 可由下一次正常记录提交写入任务台账，并在 Leader 当次交付中立即给出。不为“在当前 commit 内写自己的 SHA”反复 amend。验收通过、已提交是两个状态。

### 2.3 范围与文件归属

下文 `RAG/` 指 `deployment/AgenticRAG/`。核心、适配层、正式测试与内部 runner 在此开发。宿主最小接点仅在 R04/R12/R19–R21/R25/R26 的明确任务中修改；优先限定 `codeplus/agent.py`、工具注册、配置、现有命令处理、`__main__.py`、根打包配置及相关正式测试，具体路径由接手时扫描核对。

旧知识库清理仍属独立任务。Leader 核实其实际变更/提交后接入，不从会话标题推断已完成；有重叠文件时明确拥有者和交接基线。不得借新模块任务批量删除旧实现，也不得迁入旧格式兼容层。

冻结评测语料、题目、gold、upstream 评分器原则上只读。允许 R01/R10/R17/R23 接入新的加载/执行路径，但必须保持数据指纹和评分语义，按需同步相关正式测试。模型权重、凭据、用户数据和临时运行产物不加入 Git。

Windows 使用 pwsh 7；不用 Bash heredoc；复杂脚本写文件，验证临时文件在任务结束前清理。Windows/Linux 各用自己的环境。正式支持的测试与验收报告可以保留，报告须去除凭据和无关数据。

| 里程碑 | 任务 | 与 P 阶段的关系 | 可交付结果 |

## 6. 会话分派与交付模板

### 执行会话分派单

```text
任务：Rxx / 名称
集成目录、分支、基准 SHA、输入/spec 指纹：<实际值>
前置任务及提交：<已核对>
必须读取：<本文任务卡 + 对应 checklist + D/T/A 章节>
允许修改：<精确文件/目录及允许的宿主接点>
禁止范围：<继承改动、冻结数据、其他任务文件等>
目标与交付：<任务卡中的可观察结果>
验收：<本任务条目 + 通用实现/证据要求 + 实际环境>
完成后给 Leader：改动说明、逐项证据、实际命令/结果、限制和临时资源清理情况。
不要自行提交、推送、扩展任务或标记 Leader 验收通过。
```

### Leader 验收记录

正式记录建议按任务创建 `docs/implementation-records/Rxx.md`，开始任务时再创建；当前不预置空报告。每份包含：

- 任务/执行会话/评审会话标识，输入基线与最终审阅的补丁标识。
- 文件清单、关联 D/T/A、逐项 checklist 的 PASS/FAIL/BLOCKED 与证据链接。
- 真实命令、运行环境、输出摘要及正式报告哈希；哪些只是单元测试/模拟，哪些来自真实运行。
- 缺陷与修复记录、未完成范围、临时资源处置；Leader 最终结论及时间。
- 提交准备检查、实际 commit SHA 的交接位置、下一项任务。

台账使用 checklist 的任务状态表；新会话恢复时先对照 Git 和验收记录，不依赖聊天摘要或子会话自报“完成”。
