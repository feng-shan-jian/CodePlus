# 模型提供方与配置设计

状态：设计草案，尚未实现。更新日期：2026-09-21。关联决策：[主规划 D15、D16、D35、D36、D39–D41、D44–D46、D51、D53](plan.md)。

本文维护模型配置与切换规则；工作进程 IPC、请求身份、调度、取消和宿主计量的工程方案见 [架构与接口契约](architecture-and-contracts.md)，具体选型验证和冻结条件见 [验收计划 G0](acceptance-and-implementation.md)。方案已提出不等于本地模型或适配器已经可用。

## 1. 已确认的要求

- 首次试用采用本地 Embedding 与本地 Rerank。
- 本阶段本地 Embedding 与 Rerank 要求 NVIDIA GPU，在 Windows 验收；Linux 与 CPU 支持不在本阶段范围。回答模型继续沿用 CodePlus 配置。
- 本地模型由 CodePlus 按需启动并复用的工作进程承载，相同模型配置共享已加载实例，统一安排推理请求；RAG 核心与 Agent 继续在各自宿主进程内运行。
- GPU 优先处理问答和报告的查询编码及重排；导入/重建按小批次穿插执行并保证持续推进，调度在批次之间进行。
- 首版端到端支持中文问题检索英文资料、中文回答并引用英文原文，按 D45 单独验收；按 D46，由现有 CodePlus Agent 使用已有对话模型生成和改写英文 query，核心及 Embedding/Rerank 工作进程不另设翻译模型。
- 模型能力从 RAG 业务流程中分离，支持后续替换本地模型或接入 API。
- 对已经接入并支持相应能力的提供方，通过配置选择，不修改数据准备、检索和 Agent 业务流程。
- 迁入主模块后在 CodePlus 配置中统一指定；独立开发阶段使用相同语义的配置结构，由适配层负责装配。
- 更换 Embedding 需要重建时先提示，用户确认后自动构建；失败时说明原因，提供“重试”和“保留原版”两个选项。多次重试失败后，用户可以选择原版。
- 按 D51，导入中断后仍使用该批次记录的原模型、分块等处理配置继续；新配置用于后续操作，原模型不可用则明确报错，保留进度与已发布版本，不静默替换。

具体模型、模型 revision、推理精度、GPU 型号/最低显存、驱动与依赖组合、批大小仍需验证后确定。API 的具体协议、提供方和首批适配器范围尚未锁定。

## 2. 与现有 CodePlus 的关系

2026-09-21 只读检查：`codeplus/config.py` 的 `ProviderConfig` 保存模型、协议、地址及认证配置，`codeplus/client.py` 的 `create_client` 根据协议创建 `LLMClient`。该客户端的核心契约是对话与工具调用的流式输出。

沿用“配置选择 → 创建适配器 → 调用稳定接口”的方式，复用宿主的配置加载与认证约定。Embedding、Rerank 各自有专门的能力接口，不把向量列表和候选排序结果塞进聊天流式接口，也不为 RAG 再实现一个聊天 Agent。

| 能力 | 对外行为草案 | 配置与生命周期 |
| --- | --- | --- |
| Answer / Agent | 沿用 CodePlus Agent 与聊天模型客户端 | 由宿主模型配置决定，本次运行记录实际模型 |
| EmbeddingProvider | `embed_documents(texts)`、`embed_query(query)`，返回顺序明确的向量及模型身份信息 | 独立选择提供方；文档编码与查询编码遵循同一套兼容约定 |
| RerankProvider | `rerank(query, candidates)`，返回稳定候选 ID、排名和模型分数 | 独立选择提供方，不改写候选原文、来源或 ID |

这些是逻辑接口，不预设必须使用 ABC、Protocol、继承层级或通用插件框架。首版采用少量明确的适配器和构造函数即可。

## 3. 配置形式草案

以下只表达预期使用方式，不是当前 CodePlus 已支持的配置，也不是可直接运行的配置文件。字段命名和模型版本在正式契约阶段锁定。

```yaml
# 位于 CodePlus 同一份配置中；原聊天 providers 配置继续由宿主管理。
knowledge:
  retrieval:
    mode: auto  # 仅知识库问答与报告功能生效；字段名仍为草案。

  models:
    embedding: local_embedding
    reranker: local_reranker

  model_profiles:
    local_embedding:
      capability: embedding
      backend: qwen3_local
      model: Qwen/Qwen3-Embedding-0.6B
      revision: "<待实测后锁定的提交>"
      device: cuda

    local_reranker:
      capability: rerank
      backend: qwen3_local
      model: Qwen/Qwen3-Reranker-0.6B
      revision: "<待实测后锁定的提交>"
      device: cuda
```

后续接入 API 适配器后，添加相应 profile，再改变 `models.embedding` 或 `models.reranker` 的引用即可选择该实现。API profile 按已支持协议定义地址、模型、凭据引用、超时等字段；不能仅填任意 URL 就视为兼容。

配置职责：

- 单一配置来源：独立阶段可单独加载 `knowledge` 配置；迁移后由 CodePlus 配置加载器传入，核心包不自行再读另一份宿主配置。
- 按 D53，固定/自动检索是知识库问答与报告的功能内配置；上例 `knowledge.retrieval.mode` 只表达作用域，具体字段名待契约确定。统一存储在 CodePlus 配置中不代表全局生效，单次知识库任务覆盖也不改变普通聊天、编程任务、其他工具或宿主权限模式。
- 入口分离：`CodePlus 配置 → 适配层 → 核心配置对象 → 模型适配器`；核心不依赖 CodePlus TUI、会话或全局配置实例。
- 首次登记 profile 需要填写其必要参数；以后在已登记 profile 之间切换只改选择项。
- 校验能力类型与实际实现、必要字段和模型输入限制。缺少依赖、未知提供方、错误能力组合明确报错，不悄悄切换模型或禁用 Rerank。
- 认证信息使用宿主现有的环境变量/凭据机制，不写入索引指纹、引用、运行报告或日志。
- 一次运行开始时记录并固定实际配置；用户改配置不使同一次报告在中途更换 Rerank 或查询模型。
- 导入批次按 D51 保存已解析的处理配置与实际模型身份，而非仅保存可变的 profile 名称；续跑由批次记录装配适配器和模型工作进程请求，不读取新默认值替代原参数。原 revision、tokenizer、解析组件等无法恢复时明确失败；配置快照只记录凭据引用，不保存密钥。
- 原批次配置与用户当前期望配置分别保留，继续导入不回写用户的新配置，也不自动触发后续模型重建。固定处理身份不要求等待恢复期间模型持续驻留显存；重新加载时仍须验证实际身份与输入约定。

这里的“配置可替换”以适配器已支持该协议和模型用法为前提。新增不兼容的协议、输入模板或模型架构时可能需要新增适配器，但 RAG 业务调用保持不变。

## 4. Embedding 切换与索引兼容

R16 服务入口、状态和查询接点见 [模型切换服务](model-switching.md)。以下保留配置切换的设计约束。

切换配置与已有索引是否可继续使用是两件事。建议的设计规则：

- 每个索引版本记录实际 Embedding 身份：模型、revision/服务版本、输出维度、文档输入模板、tokenizer/预处理、pooling 与归一化等影响编码的参数。
- 查询模型必须与当前运行绑定的索引版本兼容。两个模型的向量维度相同，不能据此认定其向量空间兼容。
- 更换模型或改变文档编码约定时，重新编码需要重建的内容并生成新的索引版本；不把新向量直接混入旧索引。
- 仅变更连接地址、凭据或执行设备等运行参数时，是否可复用索引应由模型身份和经过验证的兼容约定决定，不能仅凭名称相同而跳过检查。
- 固定版本的在途任务继续使用对应索引及其查询编码配置；旧查询模型实例/可访问端点在这些任务结束前需保持可用，否则明确报错，不改用新模型查询旧向量。
- 按 D16，配置变化触发兼容检查及必要的重建提示，确认后才开始构建；新版本构建完成并校验可查询后发布。失败时说明原因并提供“重试／保留原版”，等待选择及重试期间不破坏原索引，不自动发布失败候选。
- 本地与 API 即使声称使用同名模型，也需核对实际编码方式和版本。无法证明兼容时按需要重建处理；API 未提供固定版本时记录可获取的身份及复现限制。

这部分复用主规划 D12 的版本发布和运行绑定机制，不另建第二套版本状态机。

### 4.1 重建确认与失败处理

已确认的用户流程：

```text
更换 Embedding 配置
  → 检查与现有索引是否兼容
  → 需要重建：提示受影响的知识库、原模型与目标模型
  → 用户确认
      ├─ 取消／尚未确认：不开始重建，不切换实际模型
      └─ 确认：自动构建候选索引版本
          ├─ 成功且验证通过：发布新版本，后续新任务使用它
          └─ 失败：显示原因，提供两个选项
              ├─ 重试：再次构建，仍失败则再次提供这两个选项
              └─ 保留原版：结束本次切换，继续使用旧索引及其对应模型配置
```

设计细则：

- 区分用户期望的目标模型配置与知识库实际启用的索引/模型版本。修改配置、确认重建、构建完成和切换成功分别记录，不能写成一次已成功的切换。
- 确认绑定明确的知识库范围和目标配置。多库共用模型 profile 时需列明受影响库，不能在提示一个库后暗中重建其他库；具体批量交互后续设计。
- 构建失败发生在候选版本，旧索引及当前运行所用配置不被覆盖。用户尚未选择重试或保留时显示待处理状态，不在无输入时自动重试或声称切换成功。
- 选择保留时应明确展示实际继续使用的旧模型；不能让界面显示新模型却用旧向量，也不能用新查询模型访问旧索引。
- 失败处理只保留“重试”和“保留原版”，不提供停用或删除原版的分支。旧索引、原文及历史引用不会因切换失败或多次重试而删除。
- 用户选择重试即确认再次执行同一范围、同一目标配置的构建，无需重复询问是否开始；若目标配置或范围改变，需重新说明并确认。重试应避免重复写入和重复发布，能否复用已经完成的构建结果由版本与配置校验决定。
- 多次失败后用户可选择原版。当前约定为每次失败提供选择，不凭未确认的次数阈值自动替用户决定；重试次数与错误原因记入构建记录。
- 无交互入口同样需要明确的重建授权及失败处理策略。缺少这些输入时返回待确认状态，不把空输入、超时或无终端视为确认；具体参数形式待 CLI 设计。
- 失败信息、目标配置和用户处理选择需要可恢复记录，避免重启后悄悄重新构建或把失败候选标记为成功。

选择保留原版后终止本次失败的切换意图，明确显示实际启用的模型和版本；下一次启动不应因同一份尚未整理的目标配置而反复弹出同一重建提示。期望配置与启用配置的持久化细则在实现契约中确定。

## 5. Rerank 切换与结果记录

Dense 或 BM25 单路结果、Hybrid 经核心 RRF 融合后的结果均可按本次配置进入 Rerank。按 D44，以每个 Chunk 为独立候选，精排前不合并相邻片段；候选 ID 保持与原 Chunk、版本及来源对应，见 [主规划 4.5](plan.md#45-逐-chunk-rerank)。标题/章节输入模板、候选上限及超长输入策略仍待设计。

- 单独更换 Rerank 通常无需重建向量索引；在新运行中按新配置对已召回候选排序。
- 如果新模型需要不同输入长度或模板，适配器显式处理限制；不通过修改保存的证据原文来满足模型输入。
- 输入长度按实际 Reranker 的 tokenizer 和完整输入计量，包含 query、模板及附加信息；分块时通过 Embedding 输入检查不等于精排输入已通过。实际评分范围与原文来源可关联，内部候选不自动登记为回答模型已读取的证据。
- 输出依据候选 ID 关联原始材料，不能因排序改变或批次合并而串接错误来源。
- 记录模型、版本、输入范围、候选数量、分数类型与配置指纹。不同模型的分数不直接比较，不沿用旧模型的相关性阈值而不校准。
- 在线 Rerank 失败按主规划 D25 返回明确错误，不自动退回未重排结果；自动模式的 Agent 可显式关闭 Rerank 后再次调用，固定模式保留原配置。此处的运行故障处理与 D16 的索引重建失败交互分开。
- 查询缓存及评测配置包含 Rerank 身份；切换后不能误用上一模型的排序缓存。

## 6. 首版实施与验收边界

首版本地适配器为真实执行路径，先实测 Qwen3 的 0.6B Embedding 与 0.6B Reranker 候选，再决定是否采用及如何配置。主规划记录的 8 GiB 级 GPU 仅作为资源条件，不替代性能验证。

按 2026-09-23 修订后的 D35 与 D36，本阶段验收覆盖 Windows 的 NVIDIA GPU 环境。Linux 与 CPU 执行路径留待后续；本地适配器设备不可用时明确报告驱动/运行环境、设备或显存问题，不静默切换 CPU、另一模型或外部 API。检查只针对实际启用的能力，GPU 是本地 Embedding/Rerank 的支持要求，不应因此阻断未使用本地模型的 CodePlus 基础功能。在线故障继续遵循 D25，索引重建故障继续遵循 D16。

D39/D40 已确认同机多进程并发查询及共享本地模型工作进程，D41 已确认问答/报告检索优先、导入/重建分批穿插推进。CodePlus 按需启动并复用工作进程，模型能力接口由本地客户端转交 Embedding/Rerank 请求；知识库业务和 Agent 保持宿主内职责。部署及调度边界见 [部署与迁移设计](deployment-and-packaging.md)。在途运行的模型身份继续按 D12/D15/D16 固定；相同模型配置的实例复用与不同配置的身份隔离分别验收，具体并发、优先级参数、驻留和显存上限仍需确定。

正式验收至少需要：

1. 核心代码通过能力接口调用模型，不能依赖具体本地模型类、API SDK 或宿主全局配置。
2. 文档/查询编码符合选定模型输入约定；向量数量、顺序、维度和有限数值可校验，最终输入长度可检查。
3. Rerank 返回结果可还原到原候选 ID，不能丢失来源或伪造新候选；批处理/截断行为有明确记录。
4. 配置校验、提供方选择和错误信息可验证；不支持的后端不显示为可用能力。
5. Embedding 与索引不兼容时明确阻止误用；确认前不构建，确认后自动构建，只有验证成功才发布；取消不切换，失败说明原因并提供重试/保留原版；连续失败、重试成功与选择原版均有验收，原索引不被失败构建破坏。
6. Rerank 配置切换不重建不相关的文档向量；新运行使用新配置，在途运行使用原配置。
7. 两个平台分别记录真实 GPU 推理的模型、依赖/驱动版本、设备、质量、显存/内存和耗时，并验证设备不可用及显存不足时的错误行为。接口替身测试只能证明契约与装配，不能证明 GPU 推理或外部 API 已可用。
8. 两个真实 CodePlus 客户端验证工作进程启动与复用、同配置模型实例复用、请求和候选 ID 对齐、模型版本隔离、超时/取消及退出处理；异常时遵循 D25/D16，不能悄悄在宿主再加载另一份模型或无限重放请求。
9. 按 D41 验证问答/报告请求在批次边界优先调度，持续查询时导入/重建仍有进展；分别记录排队、模型切换和推理开销，取消或超时的任务不继续占用待执行队列。GPU 批次调度不改变知识库修改互斥及版本发布规则。
10. 按 D45/D46 记录 Agent 提交的英文 query、实际传给 Embedding/Rerank 的输入和候选语言并验证质量，计入查询生成及补查开销。端到端中文问答成功不能记为模型直接以中文 query 检索英文资料已通过；未来若支持这类直接输入，需单独验证。原始中文问题、原文及索引数据不因 query 改写或输出中文而被翻译覆盖。
11. 按 D51 验证修改默认模型、同名 profile 或分块配置后重启，原导入仍按其已记录配置执行；原模型/组件不可用时明确失败而非替换，恢复兼容环境后可手动继续。核对实际模型身份、旧产物复用、当前默认值未被回写及后续新配置仍遵循 D16 的兼容与重建确认规则。

外部 API 的具体适配器实现和真实调用验证另行列入实施范围。首版可以先具备明确扩展边界，但不得把未实现的 API 适配器称为“改配置即可使用”。
