## 热模型调度实测

两个真实宿主都提交前后台负载。60个返回记录严格核对单一实际 profile、共享 worker、同一模型 UUID、load_count=1；每个后台返回完整 input_tokens=[2048,2048]。持续保有最多8个前台、3个后台在途请求，沿默认16项/4MiB等待队列，未调大配额。两类实际执行顺序均与逐次 queued 确认的提交顺序一致。

| submit→finished P95 / max | 959 / 988 ms | 1423 / 1423 ms |

60请求共5489ms，24个后台文档约4.37个/秒。相邻后台完成间隔最大500ms。44个前台选取点都有“上批完成前已收到后台 queued”的证据，均不超过连续4批；2ms余量仅处理跨宿主接收观测，不声称它是 GPU 内核时钟。FIFO与额度另由受控需求性质测试覆盖。

queue_ms 在现有实现中包含输入校验；表中纯等待近似量来自 queued/validation 阶段接收时间，仍包含 IPC 抖动。这组短热模型压力不代表所有负载的 SLA；它支持继续采用当前4:1、最多4项、4096 padded-token上限。实际GPU内核不抢占，只在完成批次边界调度。
