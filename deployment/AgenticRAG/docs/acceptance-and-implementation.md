# 验收与分阶段实施计划

更新日期：2026-09-23。状态：验收设计；实际执行进度以 [checklist](implementation-checklist.md) 为准。用户已将本阶段收敛为 R00–R24 的 Windows 独立模块功能与质量验收。

需求依据为 [主规划 D01–D56](plan.md)，对象与接口依据为 [架构与接口契约](architecture-and-contracts.md)。本文件中的 P0–P7 是能力与验收阶段，不能按文档存在就认定已完成。发行安装与主模块迁入不在本阶段验收范围。

实际会话拆分和派发顺序见 [R00–R24 任务规划](implementation-task-plan.md)，逐项通过条件见 [checklist](implementation-checklist.md)。R 任务把首次发布、Dense、原文及 Agent 的必要部分前移，R12 先交付真实问答链路，再补齐完整生命周期和检索能力。G0 先做小规模能力验证，609 篇正式建库开销由 R10 验证，worker 的正式复用/负载调度由 R09/R22 验证；这些功能与质量门槛未被省略。

## 1. 如何判断规划完成与功能完成

规划完成需要：范围与关键行为明确，接口和状态无主要矛盾，任务有依赖和验证方法，质量/成本取舍得到确认；只能靠实测决定的数值要有确定程序和失败处理。本阶段开发完成还需要实际代码与 R24 验收证据。

当前已完成主要需求澄清，D56 已确定预算内质量优先，已提出可审阅的架构、契约与阶段任务，可进入整体设计审阅。模型 revision、依赖兼容、预算与性能数值进入 G0/P7 的验证任务，尚无数据时不填写“已通过”或编造百分比。

每阶段交付记录应含：代码/配置版本、关联需求、改动范围、执行命令与环境、结果及未执行项、已知限制、下一阶段条件。正式测试进入仓库已有或新模块的正式测试体系；临时探测脚本、日志和临时数据在任务完成前删除。必要的验收报告作为正式交付保存，用户语料和模型缓存不随报告提交。

## 2. G0：先验证会影响架构的事实

G0 是 P0 的技术验证门槛，后续实现前单独执行，不在本次规划中启动服务或下载模型。

| 验证 | 有界实验与记录 | 通过 / 未通过处理 |
| --- | --- | --- |
| 依赖与 Milvus | 检查当前 Compose、服务端/客户端实际版本；隔离的测试资源执行插入、Dense、原生 BM25、强一致读取和重启读取；保留完整版本清单 | 冻结一个真实通过的组合；不把旧 pin 原样抄入新依赖。不支持的已有实例返回能力不兼容 |
| 版本隔离与成本 | 两个候选版本使用不同 Collection；新版新增高频词/删除资料，同时重复旧版 BM25 与 Dense 查询；测完整 609 文档复制/构建时间和空间 | 旧版的成员与统计不受新版写入影响；若 Collection 数/成本不可接受，提出替代协议并重新验证，不悄悄改成只加字段过滤 |
| 本地模型 | 固定候选 revision，在目标 NVIDIA GPU 实测文档/查询编码、Rerank、加载切换、峰值显存、超长/OOM、两客户端竞争 | 形成模型与输入模板兼容表；资源不足先调批次/驻留策略。改模型显式记录，不切 CPU/API 冒充通过 |
| 原文位置 | 重复段落、CRLF、Unicode、标题、表格、代码块、超长句及英文新闻样例 | 每个证据区间可还原对应原文；解析器行号与字符映射分别验证，无法映射的输入明确失败 |
| 宿主 Agent 接点 | 对照 `run` 与 `run_to_completion` 的模型调用、工具交付、流式输出、压缩、预算及退出处理 | 确定共用的最小可选策略，不新增专用 Agent 引擎；普通任务保持原行为 |
| 评测解耦 | 现有 `check.py` 依赖旧 `codeplus.knowledge.benchmark.load_dataset` 和 `models.fingerprint`；`run.ps1` 调用旧知识库模块 | 抽出依赖中立的数据读取/指纹，保证冻结数据及 hash 完全一致；替换执行接点，保留评分语义与已有命令形式 |
| 独立包边界 | 明确开发包与宿主适配导入、资源路径；核对 Windows 开发运行环境 | 验证已实现的独立包和宿主接入，不把开发环境运行说成正式发行安装通过 |

当前仓库事实只是输入：旧模型/依赖 pin、现有 Compose 版本、当前 GPU 配置都不是新模块兼容性结论。G0 报告须保存实际使用值，不引用“曾经可用”代替本次验证。

## 3. 数据与实验协议

现有 [评测说明](../../../eval/RAG-eval/README.md) 记录 609 篇英文新闻、2,556 道原题和 6,084 条证据。lite 50、medium 200、full 2,556；其中检索评分题分别为 44、177、2,255。各档使用同一完整语料，`lite ⊂ medium ⊂ full`，不是天然独立的训练/测试集。

1. 正式评测只导入 `eval/RAG-eval/corpus/`。原题、答案、gold、评分器和内部补充用例不得混入知识库。所有 609 篇必须成功发布且哈希匹配；普通导入的部分成功规则不能降低此要求。
2. 保持现有上游题目、证据、顺序、分层 ID 与评分代码的冻结口径。新适配器改变取数位置时，逐项比对原指纹；不修改 gold 来适配分块。
3. 建议 medium 200 用于开发，另存 `full - medium` 的 2,356 个 ID 为验收子集。若其中题目已参与旧实现调参，明确标为历史暴露；不能宣称“未见测试集”。full 仍作官方总体报告，同时单列开发/验收部分，不能混为无泄漏泛化结论。
4. 查询生成、Agent 和检索核心只能接收用户问题与可检索语料；参考答案/gold 只交给评分阶段。固定检索路线也不得获得 gold。
5. 每次实验冻结语料及问题哈希、模型/配置指纹、代码版本、Milvus 与系统环境、回答模型参数、预算、随机性配置和运行时间；API 模型无法完全固定时记录实际标识与日期。
6. 失败、超时和未完成题保留在相应分母中，记录独立失败原因。null_query 按官方口径不纳入检索分母，但须纳入答案/拒答验收；不能筛掉难题再报平均值。

建议新增以下**内部验收材料**，与官方结果分开，不改变官方题库：

| 套件 | 初始规模建议 | 验证重点 |
| --- | --- | --- |
| 中文问答 | 从开发部分分层选择 30 题，人工审核中文表达与原题约束 | 英文 query 是否保留问题、中文答案、英文原文摘录；不拿译文替代原文证据 |
| 研究报告 | 10 个围绕同一语料的主题/比较任务，每个预先列必答维度和已核对证据 | 多文档综合、分歧、推断标识、引用覆盖、局限和可用 Markdown 文件 |
| 多轮与继续研究 | 10 个场景，包含资料更新/删除、旧版引用、预算停止后继续 | 承接缺口、本轮重新取证、独立预算/版本、旧报告保留和累计成本 |
| 结构与生命周期 | 按 A01–A13 故障矩阵建立小型专用语料，不混入 609 篇正式库 | 原文映射、版本、恢复、并发与错误路径 |

补充套件的数量是工程建议，验收前冻结内容和 rubric。开发时反复使用的补充材料只证明功能覆盖，不宣传为未见泛化评测。

## 4. 指标口径与对照组

### 4.1 检索、Context、答案和引用分别报告

| 指标 | 定义 / 输入 | 不能据此声称什么 |
| --- | --- | --- |
| 官方检索 Hits / MAP / MRR | 沿用冻结评分器，Top-K=10；按原题型分组，错误计零 | 命中部分材料不证明多跳证据齐全；不同 Chunk 长度会影响匹配，须记录 |
| Gold Evidence Recall@K | 命中的 gold 证据单元数 / 该题全部 gold 数；匹配使用可追溯来源与区间，无法对齐单列失败 | 不能拿“命中任意一段”当成 recall=1 |
| Complete Evidence Hit@K | 该题所有必要 gold 证据都覆盖才算命中；只在有 gold 的题统计 | gold 可能不是唯一正确证据集合，未匹配不自动等于答案错误 |
| Context Relevance | 人工/固定评委判定实际送入回答模型的证据片段是否有助回答，报告相关片段占比及 token 加权占比 | 检索候选全集不等于模型所见 Context；截断/压缩后用实际输入评分 |
| Faithfulness | 将答案拆为可核查事实/推断单元，判断每个是否由本轮实际证据支持，报告支持比例与严重无依据结论 | 资料本身是否真实是另一问题；空答案标不适用并单列拒答，不能获得满分 |
| Answer Relevance | 冻结 rubric 评价是否直接回应问题及覆盖必答维度，报告分项及归一化结果 | 相关不等于正确；报告与短问答使用各自 rubric |
| 答案正确性 | 参考答案语义一致性，独立评委加人工校准；null_query 独立判断合理拒答 | 官方 `upstream_word_overlap_accuracy` 只要求一个分词重合，不充当语义正确率 |
| 引用程序有效率 | 引用 ID、运行证据资格、范围/版本/位置、直接摘录检查；另报首次通过、修正一次、最终失败 | 程序有效不证明结论得到语义支持 |
| 引用覆盖与支持 | 需要证据的结论中，带可支持引用的比例；人工审查支持是否完整 | 引用数量多不等于覆盖高；仅删除失效引用不能修复无依据答案 |
| Agent 成本 | 每题实际搜索/打开/模型调用、输入/输出/缓存 token、失败尝试、停止原因；继续研究逐轮及合计 | 多轮不保证改进；用量未知不能记为零 |
| 延迟与资源 | 端到端与解析/编码/查询/重排/模型/排队 P50、P95；冷启动、热查询、导入并发分别统计，另报峰值显存与磁盘 | 单机空闲热查询不能代表冷启动、并发和其他平台 |

离线 LLM 评委固定模型标识、提示词、版本和输入格式，评分前冻结 rubric。人工至少分层核对正确/错误、拒答、冲突、低分和高分样本，记录一致性及分歧处理。评委只出离线诊断，不接入每次在线答案的额外模型调用。无法运行评委时对应指标标未执行，不能用词重合或程序引用校验替代。

### 4.2 对照必须拆开变量

| 对照层 | 组别 | 固定因素 |
| --- | --- | --- |
| 单次检索 | Dense、BM25、Hybrid、Hybrid+Rerank | 同一版本/原始 query、相同候选和评分协议；官方 Top-K=10 输出与产品 Context 数量分开 |
| 端到端路线 | 固定模式下不同路线，均可多轮搜索/阅读 | 同一回答模型、任务类型、预算、题集和输出校验 |
| Agent 选择收益 | fixed 与 auto | 同一基础路线、回答模型及可比预算，两者都允许多轮；单列 auto 实际选择分布 |
| 补查收益 | 对同一题记录首轮证据与最终证据/答案 | 使用最终实际执行记录，成本归属完整；不把多轮合并结果伪装成单次 Top-K |
| 任务及语言 | QA、报告、中文跨语言分别评测 | 各自固定协议，不能用英文短问答分数替代报告或中文能力 |

官方检索包装器要求原题 query 和 Top-K=10；Agent 内部改写另记事件，产品运行报表和官方检索基线分开。任何合并多轮证据的诊断必须另标口径，不能修改官方协议来得到更高成绩。

报告质量采用逐项检查：任务要求维度有结论或明确资料不足；跨文档比较有双方证据；冲突不被隐去；推断与直接事实区分；引用有效并覆盖事实；Markdown 结构可读；保存结果与实际文件一致。不用报告长度或章节数量充当研究质量。

## 5. 验收门槛如何冻结

### 5.1 硬性正确性门槛

以下是正式测试与真实验收用例中的零容忍项，不是对所有未来输入的数学保证：

- 不得跨库、串版本、把未发布或失败候选作为成功证据；不得在无有效证据时交付伪称取自知识库的事实答案。
- 已发布历史原文、引用定位与用户文件不能因更新、失败、放弃或索引回收被破坏；正式评测语料完整率为 100%。
- 无效引用不能作为正式答案输出；最终失败须有明确状态；不自动模型降级、重试或扩大预算掩盖错误。
- 同库竞争修改只有一个有效拥有者；待恢复占用、崩溃恢复与迟到结果符合协议；两个真实进程验证，不能只靠单进程 mock。
- QA/报告与 fixed/auto 只在知识库功能内生效；两个真实 Agent 入口均通过；普通聊天、编程和权限语义回归通过。

### 5.2 效果、预算与等待时间门槛

产品优先级已按 D56 确定：证据与答案质量优先，可接受预算内的额外等待；成本和时延仍须有明确上限，不能无限追加。按以下程序冻结目标，避免拍一个无法解释的 Recall 百分比或时延：

1. G0 冻结环境与可用模型；P4/P5 在 medium 开发集跑单次检索基线，P6 跑真实 Agent 基线。先公布质量、错误、token、P50/P95 和资源成本，不只选最好的一项。
2. 在开发集提出具体预算与目标表：QA/报告各自的搜索/阅读/token/时间/收尾预留，Context 上限；关键质量指标最低值、相对基线的可接受回退幅度、P95 上限及测量条件。
3. 对方案的质量/成本取舍进行一次集中审阅后冻结，不在最终集成绩出来后移动阈值。若某数字仍未知，该验收项不能标为通过。
4. P7 执行冻结验收集与 full 报告；同题比较附差值和成对 bootstrap 置信区间。小样本/波动导致证据不足时标为不确定，不能把“未显著下降”自动解释为已证明不劣。
5. 未达标时记录失败并回到相关阶段修正；若更换模型/预算或调参触及验收集，披露再次使用的影响。重大产品取舍重新讨论，不靠静默缩减已确认功能过关。

初始 Chunk/候选/RRF/Context 参数见架构草案，仅是试验起点。auto 为用户确认的功能默认模式，但不能因此宣称 auto 必然优于 fixed；默认路线和预算须经过上述比较。

### 7.1 检查入口与命令约定

已有 `eval/RAG-eval/check.py`、`score.py`、`run.ps1` 保留职责和基础使用形式，P0 先解除旧实现导入依赖，P4/P6 再接新执行路径。当前直接运行它们仍可能触发旧代码，不能作为新实现验证。

以下是实施后需要提供并实际执行的检查形式，**本轮未运行，尚不保证当前 checkout 可执行**：

```powershell
# Windows，P0 解耦后：冻结数据/分层完整性检查
pwsh -File eval/RAG-eval/run.ps1 -Tier lite -Check

# P1 起建立正式测试体系后：从项目自身的 Windows 环境运行
python -m pytest deployment/AgenticRAG/tests

# P4 接好新核心后：保留基础检索命令形式，使用实际新库 ID
$newKbId = '<替换为实际的新库 ID>'
pwsh -File eval/RAG-eval/run.ps1 -Tier medium -KbId $newKbId -Mode dense
pwsh -File eval/RAG-eval/run.ps1 -Tier medium -KbId $newKbId -Mode bm25
pwsh -File eval/RAG-eval/run.ps1 -Tier medium -KbId $newKbId -Mode hybrid
```

Rerank、真实 Agent、多轮和完整故障矩阵由新模块内部 runner 组织，调用同一核心与宿主 Agent；具体 runner 参数随实现同步文档，不伪造尚不存在的产品命令。每个 runner 输出结构化原始记录与可读汇总，模型/服务失败用非零退出状态和报告表达。

Linux 采用自己的虚拟环境和 Python runner；Windows 的 `run.ps1` 当前硬编码 `.venv/Scripts/python.exe`，不能把它列为 Linux 已支持入口。P7 必须提供等价、经过验证的跨平台内部执行方式；日常用户仍使用 CodePlus 基础命令。

### 7.2 每个验收报告的最小字段

`run_manifest` 至少包含代码及配置指纹、数据/题目哈希、模型与索引实际版本、平台/设备/依赖、题集及题序、各类预算、开始/结束时间；每题保存状态、原问题、实际工具参数、搜索/阅读及交付证据、最终答案/引用、用量与停止原因；汇总同时列官方指标、新增诊断、P50/P95、失败分布和未执行项。

不要保存 API 密钥或隐藏推理文本。评测参考答案和 gold 存在评分记录侧，不进入运行提示。中间候选与实际送达 Context 分开，以便解释“召回了但未被模型看到”的失败。
