# 开源、部署与迁移设计

状态：设计草案，尚未实现或完成部署验收。更新日期：2026-09-21。关联：[主规划 D01、D02、D15、D29、D33–D54](plan.md)。

用户已明确以开源项目为目标，并在 D34 选择首版由用户各自在自己的电脑或服务器安装使用，不建设带账号和权限管理的多人共享服务。架构草案采用同进程调用独立 RAG 包；D40 进一步明确，本地 Embedding/Rerank 使用共享模型工作进程，知识库业务和 Agent 仍在各自 CodePlus 进程内。完整 RAG 服务保留为未来扩展；当前均为设计，尚未实现或完成部署验收。

## 1. 代码组织与运行方式分开

独立 Python 包描述代码、依赖与可发布边界，不要求独立进程；同一份核心包也可以被未来的服务端调用。是否独立服务描述运行、通信及资源隔离方式，不要求复制一套 RAG 业务逻辑。

| 场景 | A：同进程调用独立包 | 后续需要补充的工作 |
| --- | --- | --- |
| 迁入 CodePlus 主模块 | 可通过适配层集成同一核心 | 明确发行包布局、依赖与配置接入，验证原命令及通用 Agent |
| 开源后由用户各自安装使用 | 可以采用该方案 | 提供可安装发行包、依赖分组、配置示例及实际安装验收 |
| 在服务器或容器中运行 CodePlus | 可以采用该方案 | 配置持久化数据、Milvus 地址与模型提供方，并验证目标环境 |
| 将 Embedding/Rerank 放到其他机器 | 不必先将整个 RAG 拆成服务 | 按 D15 接入相应 API 适配器；模型/索引兼容性仍须验证 |
| 多个客户端共享一个 RAG 后端 | A 本身不提供此能力 | 增加服务端与客户端适配，以及认证、隔离、任务生命周期等契约 |
| 独立扩容与故障隔离 | RAG 核心与 CodePlus 共用进程；D40 单独承载本地模型推理 | 验证模型进程故障处理；整个 RAG 的独立扩容仍需服务化设计 |

因此 A 不构成开源或迁移的技术障碍，但“以后能服务化”不等于“以后只改一行配置就得到完整服务”。可保持核心业务不变的前提是下述边界真正落实；服务适配本身仍有实施和验收成本。

## 2. 建议保持的核心边界

- 核心只接受自己的配置、请求对象与能力接口，不导入 CodePlus 的 TUI、命令上下文、会话实例或全局配置；CodePlus 适配层负责转换和注册工具。
- 按 D53，固定/自动检索模式只归属知识库问答与报告的配置域。迁入统一配置和命令后，功能默认值及单次覆盖仍只作用于知识库功能运行，不改变通用 Agent、普通聊天、编程任务或宿主权限模式；迁移验收覆盖这一配置隔离边界。
- 管理、导入、搜索、原文读取、引用校验及运行绑定有明确输入、结果、错误和状态标识。请求/响应避免依赖进程内对象引用，为未来序列化保留空间；不提前引入通用 RPC 框架。
- 正在导入、重建、等待确认、重试、发布和回收的状态不能只存在于某个 Agent 的内存；按 D12/D16/D30/D32 由共同的持久化状态支撑。未来增加服务端时复用这些规则，不再写一套状态机。
- CodePlus Agent 继续负责问题拆解、工具调用和回答。以后如增加 RAG 服务，可先只提供知识管理、检索及来源能力；不因服务化而自动迁走或复制 Agent 主循环。
- 长耗时导入与本地模型推理不能阻塞宿主交互循环。按 D40 由共享工作进程承载本地模型、统一安排推理请求；宿主的导入任务执行与模型进程的通信、生命周期和 GPU 调度仍需细化。
- 同进程核心、远程 Milvus、远程模型是可以独立选择的维度。核心的调用方式不应强迫用户同时改变模型提供方或索引存储。

首版概念调用关系（尚未实现；未来完整 RAG 服务可另加客户端适配）：

```text
CodePlus 进程 A                     CodePlus 进程 B
命令 / Agent                       命令 / Agent
     ↓                                  ↓
适配层 → 进程内 RAG 核心             适配层 → 进程内 RAG 核心
             ↓ 模型能力接口                      ↓ 模型能力接口
             └─────────────┬─────────────────────┘
                           ↓
             本机共享模型工作进程（D40）
                Embedding / Rerank → NVIDIA GPU

各 RAG 核心按 D38/D39 协调访问本地文件、SQLite 与 Milvus。
```

## 3. 开源安装与部署建议

- 将原文归档、元数据、模型缓存、运行记录与源码/安装包分离，目录及服务地址由配置指定；不硬编码当前工作区、Windows 盘符或用户目录。移动代码目录不应改变文档及引用身份。
- 允许不启用 RAG 的 CodePlus 安装保持轻量。本地推理依赖和未来 API 模型适配依赖按能力分组。Windows 与 Linux 已按 D35 纳入首版，本地 Embedding/Rerank 按 D36 要求 NVIDIA GPU；具体依赖分组、系统版本、驱动与设备组合待实测。
- 配置可替换不等于所选 API 已实现；每个正式支持的适配器须有清楚的依赖、连接、错误与索引兼容约定，保持 D15/D16。
- Milvus 作为独立依赖继续通过明确地址连接。按 D37，首版提供 Docker Compose 配置供用户启动，也支持连接已有实例；两种方式共用客户端与检索实现，通过配置指定连接及数据范围。
- 分发代码、模型权重、容器镜像和评测数据时，分别核对所涉及许可、归属说明和必要通知；项目自己的许可证不能代替第三方材料的许可核对。不在当前草案中声称已完成全部依赖许可审核。

Python 标准项目元数据支持通过 `optional-dependencies` 定义按需安装的依赖组，适合承接上述能力分组；这仍需结合实际锁定依赖验证。[Python Packaging User Guide](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/#dependencies-optional-dependencies)

### 3.1 首版平台与验收范围

已确认 D35：首版正式支持 Windows 与 Linux。开发先在当前 Windows 环境推进，发布验收分别使用两个平台的干净安装环境；macOS 暂不纳入首版正式支持范围。

- 平台支持针对 CodePlus 与 RAG 核心的安装及运行；Milvus 的部署方式、本地模型设备、驱动和依赖版本另列部署矩阵，逐项验证。
- 两个平台都需从发行包安装，并通过现有基础命令完成建库、导入、真实模型检索、Agent 回答和引用读取；覆盖重启后数据及历史引用仍可访问。沿用前述 wheel 与 sdist 验收要求，记录环境和产物版本。
- Windows 与 Linux 分别使用各自的 Python 环境与依赖。跨平台核对路径分隔符、文件名大小写规则、中文及含空格路径，以及文本换行对解析和原文定位的影响；身份和归档规则的具体契约在数据设计中确定。
- D36 已确认首版本地 Embedding/Rerank 要求 NVIDIA GPU，CPU 支持后续补齐；最低内存/显存、驱动及性能目标仍待实测。该要求仅约束本地模型能力，不自动要求回答模型或 Milvus 使用 GPU。本轮仅更新支持目标，尚未执行平台安装或模型运行验收。

### 3.2 Milvus 部署与连接

已确认 D37：提供项目维护的 Docker Compose 部署配置及使用说明，同时支持配置连接用户已有的 Milvus 实例。

- 项目部署路径需明确容器运行环境、固定并验证的服务与客户端版本、启动方式、健康检查、端口及持久化数据。现有 `compose.yaml` 仅作为整理基础，具体版本及配置仍需针对新模块验证。
- 连接已有实例时，通过配置指定服务地址、必要认证/传输设置及新模块的数据范围；只管理分配给本模块的资源。连接已有 Milvus 不延续旧 RAG 索引或引用格式，仍按 D10 建立新库。
- 开发、评测和用户数据需有可核查的隔离规则。Compose 项目/数据卷、Milvus 数据库或集合的归属和命名在实现契约中确定，避免重复安装或评测覆盖已有数据。
- 两种连接方式使用相同的版本、检索和错误契约。连接失败、认证失败、服务未就绪及版本/能力不兼容应明确区分；失败遵循 D25，不自动切换另一个实例或创建空库冒充成功。
- 验收包含安装包内的部署资源可用、按说明启动后的真实读写、重启后索引可读，以及已有实例的配置连接和资源隔离。配置文件存在或端口可达不足以证明检索可用。

当前仅确认部署交付范围，未启动服务、调整现有 Compose 或操作 Milvus 数据。原文归档与版本元数据按 D38 采用下述本地存储方案。

### 3.3 本地存储与数据职责

已确认 D38：首版使用可配置的本地文件目录与 SQLite，Milvus 继续负责检索索引。

| 存储 | 保存内容 | 职责边界 |
| --- | --- | --- |
| 本地文件 | 导入时的原件快照、历史引用需要的解析归档及来源映射内容 | 独立于原始导入路径和源码目录保存；历史版本不被新导入覆盖，遵循 D31 |
| SQLite | 库与文档身份、版本清单、归档引用、引用定位关联、模型/索引配置、导入和运行状态、占用及恢复记录 | 作为业务元数据的权威记录；具体表结构、单库/多库数据库文件布局待定 |
| Milvus | 按 D42 管理 Dense 与内置 BM25 索引及检索所需字段，并关联已发布版本 | 索引可按 D32 回收；历史原文及引用读取不依赖已回收索引；分析器、BM25 统计范围及物理版本布局仍需验证 |

设计约束：

- 运行数据与源码、安装包及模型缓存分开。具体数据目录可配置，文档/版本/引用身份不能由安装目录推导；路径迁移不改变历史身份。
- SQLite 事务仅覆盖数据库自身的数据。文件归档、索引准备及版本发布需要共同的状态与恢复协议：完成并验证候选资源后才发布可见版本，失败不破坏已发布版本。不能以一次数据库提交替代 D12 所要求的跨存储一致性。
- 按 D47，普通批量导入在整批处理结束后只发布一次成功变更，处理期间维持原已发布版本；首次建库未发布时明确不可查询。中断不能触发提前发布；发布附近中断时先核对实际状态，避免把响应丢失当作发布失败或重复生效。
- 按 D48 保留可在进程重启后使用的导入进度，由用户手动选择继续。恢复记录须关联批次、输入与配置身份、完成阶段和产物、基准版本及实际发布结果；取得执行权并校验后复用有效结果。进度写入与产物完成的协议须容忍中途退出，不能仅因状态写为成功就跳过实际完整性核对；所需资源按 D32 保护。
- 按 D50 在解析/Embedding 前保存本批输入清单及逐文件快照结果，续跑从已验证的不可变原件读取，不依赖当前源文件内容。快照未保存完整或损坏时明确报告，不能静默换成新内容；原件存储可与正式归档复用，仍需区分临时碎片、恢复依赖及历史归档，验证采集和落盘中断、容量不足及源文件后续变化。
- 按 D51 保存批次已解析的处理配置和模型/组件身份，重启后的续跑仍使用原配置；只保存配置名不足以保证恢复。原模型或组件无法取得时明确失败，不混用新结果；当前用户配置保持不变，恢复记录只保存凭据引用。两平台需实际验证重启后装配原配置及依赖不兼容时的行为。
- 模型推理、文件解析和 Milvus 建索引不占用长时间数据库写事务；运行绑定、发布及回收资格校验通过短事务和必要的并发保护实现。多进程行为按 D39，具体占用和恢复机制仍待实现契约细化。
- 备份/迁移需覆盖相互对应的 SQLite 元数据与原文归档，并明确索引是同步迁移还是按记录重建；恢复后验证版本、原文引用和可检索状态。具体备份入口和恢复步骤在实施任务中设计。
- 数据访问接口允许未来新增后端，但切换数据库或归档存储仍需完成数据迁移及引用完整性验证。D38 不引入旧 RAG 格式兼容，继续遵循 D10。

SQLite 官方将应用本地存储列为适用场景，并说明每个数据库同一时刻只有一个写入者。本设计据此采用短事务和明确的写入协调，并将 SQLite 数据文件放在宿主本地存储，不采用多机直接写入共享文件的方式。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

### 3.4 同机多进程与修改任务互斥

已确认 D39：同机多个 CodePlus 进程可以同时查询同一知识库；同一库的导入、更新、删除及重建等修改任务同时只执行一个。冲突时返回明确的忙状态及稍后重试提示，不默认为用户排队提交另一次修改。

- 每个问答运行按 D12 绑定开始时已发布的版本。构建候选及发布新版本时，已有运行继续读取原版本，新运行绑定最新已发布版本。
- 所有修改入口，包括批量导入、失败项重试及索引重建，使用同一套按库标识管理的跨进程占用规则；同时申请时最多一个获得执行权。具体锁机制、状态字段及恢复过程随后设计。
- 修改任务互斥是业务操作占用，不是在整个导入期间持有 SQLite 写事务。查询仍可登记运行、维护版本占用及记录结果；读任务与修改任务各自使用短事务协调。
- 占用释放需核对任务及拥有者，不能由另一进程随意解除。异常退出后核实执行与发布状态再恢复，不发布不完整候选；索引占用及回收继续遵循 D32。D16 的待确认、失败待选择与重试阶段如何持有或重新取得修改占用，需在同一状态协议内确定。
- 按 D49，待恢复的普通导入须先继续完成或主动放弃，才允许同库新的导入、删除或重建。业务等待状态须跨进程持久化，所有修改入口一致检查；等待期间不持有长数据库事务或持续占用 GPU，已发布内容查询及其他库修改仍可进行。
- 继续与放弃须互斥，主动放弃先核对实际发布状态，并确保原拥有者及迟到结果不能再发布候选，再解除新修改限制。只清理确认无依赖的候选索引和临时产物，保留历史原文、已发布版本及必要任务记录；具体状态转换、拥有者校验和清理协议随后设计。
- 不同知识库的修改不因本决策共用一把业务写锁，但共享 SQLite 或 GPU 仍会有资源竞争；实际运行并发与容量另行验证。
- GPU 模型加载、推理排队与取消独立于库修改占用设计。允许多个问答并行推进，不代表多份模型已经能够同时驻留显存。

验收应使用真实的两个 CodePlus 进程，覆盖并发查询、竞争修改、忙状态、版本发布前后读取、进程异常退出及运行占用与回收竞争。按 D48 验证重启后手动继续、产物复用与无效结果识别、竞争接管、发布响应丢失核对及恢复依赖保护；按 D49 验证待恢复时同库新修改被拦截、查询及其他库修改可用、继续与放弃竞争、完成或放弃后解除限制，以及迟到结果无法重新发布。线程内或模拟锁测试不能替代跨进程验收。

### 3.5 共享本机模型工作进程

已确认 D40：由 CodePlus 按需启动并复用本机模型工作进程，相同模型配置共享已加载实例并统一安排推理请求；工作进程只承担 Embedding/Rerank，RAG 核心、知识库发布和 Agent 仍在各自宿主内。

以下是需要落实的设计约束，具体实现与数值仍待细化：

- 两个客户端同时首次调用时协调启动及连接，避免各自创建重复模型进程。共享范围需按本机用户、设备及运行时兼容性定义；不同 CodePlus 版本的协议兼容和不兼容诊断须明确。
- 以经过解析的模型身份、revision、输入约定、精度及设备等配置决定实例复用，不能仅凭 profile 显示名称合并。旧版本在途查询与新模型重建按各自固定配置执行，多配置驻留及资源不足处理需实测。
- 每次请求携带调用归属、固定模型配置、输入及候选 ID、截止时间；返回结果对应原请求，记录排队与推理耗时。排队时间计入调用和 Agent 的耗时预算，不因排队重置 D14 的上限。
- 按 D54，知识库问答与报告各自的运行预算由宿主适配层装配并绑定，使用共同的计量、截止时间与取消契约。预算类型不改变 D41 的优先类别，不因报告预算更大就绕过共享调度，也不成为 CodePlus 其他功能的全局限制。
- 单个客户端退出或取消不终止其他客户端的调用。排队取消、计算中取消的完成边界、结果丢弃以及闲置退出策略在生命周期契约中明确。
- 工作进程异常、通信断开或显存不足时，关联调用明确报告失败，遵循 D25 或 D16；不无限重放、不静默切换 CPU/API，也不在宿主重新加载另一份模型绕过共享约定。后续恢复与重新连接策略需有界且可观察。
- 两个平台均从实际安装包启动工作进程，验证资源路径、依赖、启动竞争、两个客户端复用、模型身份隔离、客户端退出及异常恢复；不能依赖开发目录，也不能用磁盘模型缓存命中代替内存实例复用证据。

D41 已确认下述调度原则；批大小、队列容量、并发数、闲置时长或通信技术仍待细化。本轮未启动工作进程或执行性能验收。

### 3.6 问答优先与后台任务推进

已确认 D41：GPU 优先处理问答和报告的查询编码及 Rerank；导入/重建以有限批次穿插执行，并保障后台任务持续取得进展。优先级在批次之间生效，具体批大小和等待上限通过实测确定。

- 请求用途由调用路径标记，问答与报告的查询请求均属优先类别，导入/重建的文档编码属后台类别。报告多轮搜索仍受自身运行预算及共享调度约束。
- 采用批次边界调度，不依赖中断正在运行的 GPU 计算。后台任务需分批提交，避免单次过大任务独占推理进程；批次 Token 上限、并发数与模型切换策略随后确定。
- 持续有查询到来时也需安排后台批次，避免导入/重建无限等待。具体采用等待时长提升、配额或加权调度等机制在实现方案中选择，并验证多客户端之间的公平性。
- 排队和模型切换耗时计入调用及运行预算，并与推理耗时分别记录。取消或超过截止时间的请求及时退出待执行队列；已经运行的计算按取消完成边界处理，不能将迟到结果当成本次正常成功。
- 让出 GPU 批次不释放 D39 的同库修改任务占用；整次导入/重建仍按同一状态及发布规则推进。其他修改冲突继续提示忙，正在问答的运行继续使用 D12 绑定版本。
- 验收覆盖长导入期间新问答到来、持续多轮查询下后台进展、多客户端排队、过期和取消、模型切换开销；分别记录查询等待及后台吞吐，不仅报告单任务空闲环境的推理耗时。
