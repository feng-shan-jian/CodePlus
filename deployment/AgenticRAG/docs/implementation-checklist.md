## 1. 状态与证据规则

- 状态：`TODO → RUNNING → REVIEW → ACCEPTED → COMMITTED`；有问题回到 `RUNNING`，缺环境/输入为 `BLOCKED`。`ACCEPTED` 才能本地提交，`COMMITTED` 才默认进入下一任务。
- 每条任务检查必须有 PASS/FAIL/BLOCKED 结论和证据位置，记录于对应 `docs/implementation-records/Rxx.md`。成功的程序退出码、真实环境输出和人工评审结论分别说明。
- 必需项不允许用“暂未实现、后续再说、mock 通过、环境缺失”勾选。通用项确实不适用于纯文档/探针任务时，由 Leader 写具体理由；任务专属条目不能自行删减。
- 阶段性职责已在任务卡中明确：例如 R09 不验收完整负载公平性，但必须由 R22 承接。不得把整项首版要求标为不适用。
- 调整任务拆分时保留原 ID 及变更记录，可增加子项；同步依赖、需求映射和未完成列表，再派发。不得靠改验收口径让失败结果通过。

## 2. 每项任务适用的通用检查

以下条目在每份任务记录中复制并填写一次，本文件作为模板保持未勾选。

### 分派前

- [ ] G01 前置任务已验收提交，实际基线 SHA、spec/数据版本与执行目录一致；未跟踪文件也已核对。
- [ ] G02 明确执行会话、唯一写入者、允许文件、继承改动保护清单及旧清理任务的文件交接；没有两个会话并发修改同一范围。
- [ ] G03 执行者收到具体 Rxx 卡、对应 checklist、关联 D/T/A 和交付格式；环境/依赖缺口已列明。

### Leader 验收

- [ ] G04 Leader 独立阅读实际改动，检查职责和需求符合性；没有新增另一套 Agent/业务状态机或改变无关对外行为。
- [ ] G05 任务专属条目逐一有证据，正式测试覆盖真实风险；涉及调用方、数据/Schema、配置及接口的变更同步更新对应内容。
- [ ] G06 执行命令、cwd、环境、数据/模型/配置指纹、退出码、报告位置齐全；mock、单测、真实模型/服务/多进程/安装证据明确区分。
- [ ] G07 所有阻塞性缺陷已修复并重验受影响项；不存在必要用例未执行却标通过，指标失败未被过滤。
- [ ] G08 审阅指向确定的代码差异和新文件内容；后续修复/冲突解决没有落在已失效的验收结论上。
- [ ] G09 按用户 2026-09-23 最新要求，临时验证资源已有归属和实际状态记录，供用户另派的清理收敛会话接管；主线不再以清理完成作为功能验收、提交或后续任务的门槛。正式测试/报告按约保留，凭据、权重、用户语料未进入提交范围；清理若改变已验补丁，仍重验受影响项。
- [ ] G10 交付文档、使用帮助和状态与实际一致，未来能力、阶段限制及未完成工作没有被写成已完成。

### 提交前后

- [ ] C01 Leader 最终结论为 ACCEPTED，必需项无 FAIL/BLOCKED，引用具体验收记录；执行者自报成功不能代替此结论。

- [ ] C03 暂存差异与通过验收的补丁一致，相关必要检查及 `git diff --cached --check` 通过；差异变化则重验。
